Accessibility

The browser knows what an [^agecheck^] element is. So the browser gives the element its role, its name, its keyboard handling and its focus return. A site does not need ARIA to make the element usable.

Role

The user agent MUST expose an [^agecheck^] element to the platform accessibility API with one fixed role. The role is either button or checkbox, as the role question describes. The role does not change after a successful check.

Should assistive technology see the element as a checkbox or as a button?

A checkbox can say that the check succeeded. The element would expose aria-checked="false" at first, then aria-checked="true" and aria-readonly="true" after success. A checkbox also matches how the form submits the element: an entry after success, nothing before, like an unticked checkbox. ARIA 1.2 lists aria-required as supported on the checkbox role, so the required attribute maps cleanly. But people may not expect a checkbox to open a prompt. ARIA 1.2 also deprecates aria-haspopup on the checkbox role, so a checkbox cannot warn that the element opens a prompt.

A button with aria-haspopup="dialog" sets the right expectation. But no button state can say that the check succeeded. aria-pressed turns the button into a toggle, and aria-expanded turns the button into a disclosure. ARIA 1.2 does not list aria-required as supported on the button role, so the required attribute has no standard mapping.

The keys that start a check depend on this choice too. The editors would like advice from accessibility experts.

Accessible name

The user agent MUST compute the element's accessible name with the same steps HTML-AAM gives for the button element:

  1. If the element has an aria-label or an aria-labelledby attribute, use the accessible name computation from Accessible Name and Description.
  2. If the name is still empty, use the text of the element's associated label elements, joined in tree order with spaces. If a label contains the element, leave out the element's own text from that label's text.
  3. If the name is still empty, use the text of the element's contents.
  4. Otherwise, use the element's title attribute.

So the name comes from text a person can see. A person using voice control can say the words on the element or on its label.

States

  • When the element is disabled, the user agent MUST expose the element as disabled.
  • When the element has a required attribute, the user agent MUST expose the element as required, where the chosen role supports a required state. See the role question.

Keyboard and press actions

The element is a focusable area and is sequentially focusable by default, as says. A person MUST be able to start a check with the keyboard alone.

The keys that start a check follow the platform's conventions for the element's role. For the button role, those keys are Enter and Space. The user agent MUST treat a press action from assistive technology, such as a screen reader's default action, as a trusted activation of the element. The press also gives the page transient activation, as a click does. lists every way a check can start.

Focus return

The prompt takes focus away from the page. When the prompt closes, the person needs to land where they left off. When the user agent shows its prompt for an [^agecheck^] element |element|, the user agent MUST run these steps:

  1. Let |previous| be the focused area of the document of |element|'s node document, as the prompt opens.
  2. Wait until the prompt closes, for any reason.
  3. If |element| is still a focusable area, run the focusing steps for |element|, and return.
  4. If |previous| is still a focusable area, run the focusing steps for |previous|.

Focus returns before the user agent fires change or error. So a site's event listener sees focus on the element, and a message the site writes next to the element is the next thing a keyboard user reaches.

When the user agent skips its prompt, focus does not move.

The prompt

The prompt belongs to the browser or the platform, not the page. Its accessibility is still in scope. The prompt should meet WCAG 2.2. Where the prompt is not web content, the prompt should meet WCAG 2.2 as WCAG2ICT describes. The prompt exposes its content to assistive technology with the right names, roles and values. The prompt does not rely on one sense or one way of interacting. The prompt gives people enough time.

The prompt ignores input for a short time after it appears, as prompt requirements says. During that time, the prompt MUST tell assistive technology that the prompt is not ready yet. Otherwise a person using assistive technology has to guess why their input does nothing.

Open questions

After a check, the element fires change or error, and the user agent announces nothing on the page. The explainer advises each site to write its own message into a live region: a part of the page that screen readers announce when it changes. The live region starts empty, so screen readers are already watching it when the text arrives. The site also never moves focus on its own.

That advice is not a requirement, so a screen reader user depends on each site following it. Should this specification state the advice as an authoring requirement? Should the user agent announce the outcome itself, for example through a state change on the element?

After a successful check, a press on the element does nothing and fires no event, as says. A screen reader user who presses again hears nothing, and the page cannot answer. A sighted user may see a message the page already showed, but a screen reader user may have missed that message.

Should that press fire an event, so the page can answer? A checkbox role would expose the success as a checked state, which helps. A button role has no state that can carry the success. See the role question.
