Integration with HTML

The HTML Standard lists form controls by name in many places. A new form control has to join each list. This section names every place that needs a change. Each patch names the target section, quotes the current words, and gives the new words. Added words are marked as insertions.

Some places need no change, because a rule already covers every element in a category. Those patches say so and say what the editor checked.

Form categories

Target: Categories in the forms section. Each list below is a list of element names. The patch adds agecheck to five of them.

  • Form-associated elements. Current list: "button fieldset input object output select textarea img form-associated custom elements". New list: add agecheck after button.
  • Listed elements. Current list: "button fieldset input object output select textarea form-associated custom elements". New list: add agecheck after button.
  • Submittable elements. Current list: "button input select textarea form-associated custom elements". New list: add agecheck after button.
  • Resettable elements. Current list: "input output select textarea form-associated custom elements". New list: add agecheck before input. The element joins because a form reset clears {{HTMLAgeCheckElement/meetsAge}}, through the reset algorithm.
  • Labelable elements. Current list: "button input (if the type attribute is not in the Hidden state) meter output progress select textarea form-associated custom elements". New list: add agecheck after button.

The element does not join the autocapitalize-and-autocorrect inheriting elements. The element takes no typed text.

The element is never a button in the forms sense, and never a submit button. So requestSubmit() keeps throwing a {{TypeError}} when a page passes an agecheck element as the submitter.

Content categories

Target: the kinds of content in the "Semantics, structure, and APIs of HTML documents" section. Add agecheck to each of these lists, in alphabetical order:

  • Flow content.
  • Phrasing content.
  • Interactive content. The list today starts "a (if the href attribute is present) audio (if the controls attribute is present) button details". The new entry goes before audio, with no condition.
  • Palpable content.

The element's own definition, in , lists the same categories.

Disabled

Target: disabled, in "Enabling and disabling form controls: the disabled attribute".

Current text of the first condition:

the element is a button, input, select, textarea, or form-associated custom element, and the disabled attribute is specified on this element (regardless of its value); or

New text:

the element is a button, input, select, textarea, agecheck, or form-associated custom element, and the disabled attribute is specified on this element (regardless of its value); or

The second condition already covers a descendant of a disabled fieldset. That condition names no element, so an agecheck inside a disabled fieldset becomes disabled with no further change. The same section then says a disabled element is barred from constraint validation, again for every element.

Actually disabled

Target: actually disabled, in "Disabled elements". The list today starts "a button element that is disabled".

New list item, after "a textarea element that is disabled":

an agecheck element that is disabled

This change matters beyond selectors. HTML's focusable area table excludes an element that is actually disabled.

Pseudo-classes

Target: Pseudo-classes.

:enabled. Current text:

The :enabled pseudo-class must match any button, input, select, textarea, optgroup, option, fieldset element, or form-associated custom element that is not actually disabled.

New text:

The :enabled pseudo-class must match any button, input, select, textarea, optgroup, option, fieldset, agecheck element, or form-associated custom element that is not actually disabled.

:disabled needs no change. The rule reads "any element that is actually disabled", and covers the element.

:active. The list that decides when an element is being activated starts "If the element is a button element". Add a new entry after the entry for input buttons, sharing the same outcome ("The element is being activated if it is in a formal activation state"):

If the element is an agecheck element

:required. Current list: "input elements that are required; select elements that have a required attribute; textarea elements that have a required attribute". New list item:

agecheck elements that have a required attribute

:optional. Current list: "input elements to which the required attribute applies that are not required; select elements that do not have a required attribute; textarea elements that do not have a required attribute". New list item:

agecheck elements that do not have a required attribute

:default needs no change. Its list names default submit buttons, checked input elements and selected option elements. An agecheck element is none of these. :valid and :invalid need no change, because they apply to every candidate for constraint validation.

Should :checked match an agecheck element whose {{HTMLAgeCheckElement/meetsAge}} is true? A match would let a site style the success state with no script. The answer depends on the checkbox or button question in .

Entry list

Target: constructing the entry list. The list of cases where the loop continues to the next field gains one case, after the case for an unchecked radio button. HTML also needs a definition of the element's value. gives the exact words for both changes. The agecheck entry says what the entry holds.

The existing steps already skip a field that is disabled, and a field whose name is missing or empty. Those steps need no change.

Form reset

Target: Resetting a form. The current text says to "invoke the reset algorithm of each resettable element whose form owner is form". The text needs no change. makes the element resettable, and agecheck reset algorithm gives its reset algorithm.

Constraint validation

Target: Constraints. Three rules already cover the element once it joins the categories:

  • "A submittable element is a candidate for constraint validation except when a condition has barred the element from constraint validation." The element is submittable.
  • "If an element is disabled, it is barred from constraint validation."
  • HTML bars a button that is not a submit button. That rule sits in the button definition, so it never reaches an agecheck element.

Today only input, select and textarea have a required attribute. The element defines its own required attribute in . One note in HTML lists the elements that can be suffering from being missing. Current text of that note:

When a control has no value but has a required attribute (input required, textarea required); or, more complicated rules for select elements and controls in radio button groups, as specified in their sections.

New text:

When a control has no value but has a required attribute (input required, textarea required); or, more complicated rules for select elements, agecheck elements, and controls in radio button groups, as specified in their sections.

Implicit submission

Target: Implicit submission. No change. HTML defines "a field that blocks implicit submission" as an input element of certain types, so an agecheck element never blocks implicit submission. The Enter key on a focused agecheck element starts a check, as says. The key press does not submit the form.

Label

Target: The label element. makes the element labelable. HTML lets each platform choose what a click on a label does. The agecheck element needs one fixed rule, so script cannot start a check through a label. Current text:

The activation behavior of a label element for events targeted at interactive content descendants of a label element, and any descendants of those interactive content descendants, must be to do nothing.

New paragraph, right after that text:

If a label element's labeled control is an agecheck element, then the label element's activation behavior, given event, must be as follows. If event's isTrusted attribute is true, then fire a synthetic pointer event named click at the labeled control, without the not trusted flag. Otherwise, do nothing.

The click() method fires its event with the not trusted flag set. So a script that calls click() on the label never starts a check.

Interactive descendants

No change. Three rules already refer to interactive content, so brings the element under each one:

  • The button content model: "Phrasing content, but there must be no interactive content descendant and no descendant with the tabindex attribute specified."
  • The a content model: "Transparent, but there must be no interactive content descendant, a element descendant, or descendant with the tabindex attribute specified."
  • The label activation rule quoted in , and the label content model: "no descendant labelable elements unless it is the element's labeled control".

Focus

Target: The tabindex attribute. The list that starts "Modulo platform conventions, it is suggested that the following elements should be considered as focusable areas and be sequentially focusable" names button elements. New list item, after "button elements":

agecheck elements

The focusable area table needs no change. Its first row already excludes an element that is actually disabled or inert.

Sanitization

Target: Sanitization constants. No change. HTML builds the built-in safe default configuration from each element's own Sanitization entry. The element's definition, in , gives the category "Uncategorized", as for button and label. None of the element's attributes holds a URL, so the entry names no navigating URL attributes.

Sandboxing

Target: Sandboxing. Three flags touch the element. The editor decided each one:

  • The sandboxed forms browsing context flag "blocks form submission". A blocked form never sends the element's entry, so this flag needs no change.
  • The sandboxed modals flag applies. The flag "prevents content from using any of the following features to produce modal dialogs", and the browser's age prompt is modal. New list item, after "the beforeunload event":
    the agecheck element
    So a check in a document with this flag fires error.
  • The sandboxed origin browsing context flag forces an opaque origin. The prompt must name the site, and an opaque origin has no name a person can read. No new flag is needed, but the check needs a rule.

A sandboxed iframe never runs a check, because only a top-level document can. A sandboxed document can still be top-level, for example through the sandbox directive of Content Security Policy, or through a popup that inherits its opener's flags.

The check in needs two new early failures: when the document's active sandboxing flag set has the sandboxed modals flag, and when the document's origin is opaque. Both should fire error with a console message, like the top-level failure.

Parser

Target: The "in body" insertion mode. No change. The editor checked three rules:

  • "Any other start tag" says: "Reconstruct the active formatting elements, if any. Insert an HTML element for the token." The tag agecheck has no rule of its own, so the parser creates an ordinary element.
  • The element is not on the list of elements with special parsing rules. An agecheck start tag therefore does not close an open agecheck, unlike a button start tag. Nested agecheck elements break the content model but still parse.
  • Create an element for the token associates "a form-associated element and not a form-associated custom element" with the form element pointer. makes the element form-associated, so the parser gives it a form owner the same way.

The element interface for the name agecheck comes from the rule "if this specification defines an interface appropriate for the element type corresponding to the local name name, then return that interface", in Elements in the DOM. The element's definition supplies {{HTMLAgeCheckElement}}, so that rule also needs no change.

Rendering

Target: Form controls (the user agent style sheet), Native appearance, Button layout, and a new subsection under Widgets. gives the exact rules and words.

Companion documents

The element's definition links its accessibility considerations to two W3C documents, as the button element does: ARIA in HTML for authors and HTML Accessibility API Mappings for implementers. Both documents need new rows. lists the exact rows. The rows depend on the open choice between a checkbox role and a button role.
