Digital Credential Payment Method

Copyright © 2026 Apple Inc.

This specification defines a payment method for the [[[payment-request]]], identified as `digital-credential-payment`. It lets a merchant request payment from a payment instrument a user holds in a credential manager. The user selects an instrument and authorizes the payment; in return, their credential manager produces a cryptographically verifiable proof of that authorization, bound to the merchant, the amount, and a one-time challenge. That proof is represented as a digital credential, using the presentation machinery of [[digital-credentials]]. By design, the merchant orchestrates checkout (amount, instrument selection, price updates) but never enumerates, or learns the identity of, the user's credential managers, instruments, or credentials.

This document has not been reviewed or endorsed by the W3C Web Payments Working Group.

Introduction

The [[[payment-request]]] gives a website a browser-mediated checkout flow, but leaves the means of payment for each payment method to define. The presentation mechanism of [[digital-credentials]] separately lets a credential manager release a credential to a website under the user's control, though that mechanism is not itself a way to pay. This specification composes the two: the `digital-credential-payment` payment method authorizes a payment by having the user's credential manager present a credential that backs a payment instrument the user has chosen, producing a proof the merchant can cryptographically verify.

This payment method uses the [[[payment-request]]] for:

  • Checkout orchestration and user interface.
  • Shipping and contact information collection.
  • Price negotiation (e.g., surcharges, discounts, incentives).

And [[[digital-credentials]]] for:

  • User-authorized presentation of the credential backing the selected instrument.
  • Producing that [=presentation=] in response to a merchant-signed [=presentation request=].

The interaction between these two specifications works as follows:

  • The merchant provides a DCQL query [[OPENID4VP]] describing the [=credentials=] it accepts when constructing the {{PaymentRequest}}; the browser uses it to filter the [=instruments=] it shows.
  • At final confirmation, the merchant signs a final [=presentation request=] (with the negotiated amount) via the {{PaymentAuthorizeEvent}}.
  • The browser relays this signed request to a credential manager once, at final confirmation.
  • Browsers use a native, non-Digital-Credentials [=metadata interface=] to obtain non-PII instrument metadata for display and pricing negotiation.

Goals and scope

  • Enable merchants to accept credential-backed payments through existing Payment Request integration patterns.
  • Allow browsers to reuse the Payment Request UI and lifecycle for credential-backed payments.
  • Enable price negotiation based on selected payment instrument type.
  • Support cryptographically-bound transaction authorization through signed [=presentation requests=].

The following are out of scope for this specification:

  • Definition of specific credential types or formats.
  • The [=metadata interface=] implementation details (which are platform-specific).

Model

This section defines the concepts and terminology used throughout this specification.

Terminology

Terms defined in other specifications (e.g., [=user agent=] and [=payment method=]) are used as-is and link to their authoritative definitions; this specification does not restate them.

payment method
Defined in [[payment-request]]; this local proxy makes references to it normative (the source definition is informative).

The terms below are introduced by this specification to describe concepts that are not standardised elsewhere. This specification deliberately does not commit to the [[VC-DATA-MODEL]] vocabulary: the Digital Credentials API this specification builds on is format-agnostic, and at least one targeted format (ISO/IEC 18013-5 mdoc) is not a [[VC-DATA-MODEL]] credential. Where format-specific concepts are needed (e.g., "Verifiable Presentation" or "DeviceResponse"), the relevant section names them explicitly and points at the format's own specification.

This specification distinguishes a presentation protocol, identified by a Digital Credentials API protocol value (e.g., OpenID4VP [[OPENID4VP]] or ISO/IEC 18013-7), from a credential format (e.g., SD-JWT VC or mdoc). One protocol can carry several formats: OpenID4VP, for example, carries both SD-JWT VC and mdoc credentials.

credential
The data object held by a [=credential manager=] that backs an [=instrument=]. Its concrete data model depends on the credential format in use (e.g., an SD-JWT VC, an ISO/IEC 18013-5 mdoc, or a Verifiable Credential per [[VC-DATA-MODEL]]).
presentation
The credential manager's signed response to a [=presentation request=], in the form defined by the presentation protocol identified by the request's protocol (e.g., an OpenID4VP response carrying an SD-JWT VC presentation, or an mdoc DeviceResponse). This specification refers to the protocol-specific output uniformly as a [=presentation=]; it does not require any particular underlying data model.
Instrument
A credential-manager-level abstraction representing a single payment capability (e.g., "Visa ending in 1234"). One [=credential=] may back one or more instruments.
Presentation Request
A structured request from a merchant specifying which [=credentials=] and claims are required. The exact shape depends on the presentation protocol in use (OpenID4VP or ISO/IEC 18013-7; see [[[#supported-presentation-protocols]]]) and is therefore defined here as a spec-level concept rather than a single concrete schema.
Metadata
Non-PII information about an [=instrument=] (network, funding type, etc.) used for display and pricing.
Metadata Interface
A platform-specific mechanism through which the [=user agent=] obtains non-PII [=metadata=] for payment [=instruments=] from [=credential managers=]. Its transport is platform-specific; the data it carries is defined in [[[#metadata-interface-data-model]]].

Design assumptions

This specification assumes that [=user agents=] have a platform-specific mechanism to communicate with digital [=credential managers=] that allows agents to obtain public, non-PII [=metadata=] for each payment [=credential=] (brand, scheme, funding type, etc.).

The transport of the [=metadata interface=] is platform-specific: each platform vendor defines its own synchronization protocol between [=credential managers=] and the [=user agent=]. The data it carries is defined in [[[#metadata-interface-data-model]]]. The requirements below are placed on the [=user agent=], because it controls what crosses the merchant boundary. A [=user agent=] that exposes payment [=metadata=] obtained through any means MUST ensure the data path it actually exposes to the merchant satisfies the requirements below, regardless of which platform component originally produced the values.

  • The [=user agent=] MUST NOT cause the [=metadata interface=] to perform signing, and MUST NOT surface [=presentations=] obtained through it.
  • The [=user agent=] MUST apply data-minimization filtering before exposing any [=metadata=] field to the merchant: only fields defined by this specification (see {{DigitalCredentialMetadata}}) may cross the merchant boundary.
  • The [=user agent=] MUST NOT expose PII (such as full PAN, name, address) to the merchant via any field of {{DigitalCredentialMetadata}} or {{DigitalCredentialMethodDetails}}, even if the underlying platform [=metadata interface=] returns such values.

Because the [=metadata interface=] is platform-specific, two conforming [=user agents=] running on the same platform may surface different [=instrument=] sets for the same user, with no portable definition of "stale". It is acknowledged this may create an interoperability gap; see [[[#open-issues]]].

[=Credential managers=] are a separate conformance class (see [[[#wallet-requirements]]]), but these requirements are placed on the [=user agent=] because the data the merchant ultimately observes passes through it. A [=user agent=] integrating a [=metadata interface=] implementation that does not yet enforce these constraints MUST filter at the boundary it controls.

Metadata interface data model

For each payment [=instrument=], the [=metadata interface=] MUST provide an instrument record with the following items:

Instrument identifier
An opaque value, scoped to the [=credential manager=], that the [=user agent=] uses to constrain the Digital Credentials API invocation to this [=instrument=]. It is never exposed to the merchant.
Credential format and type
The credential format of the [=credential=] backing the [=instrument=] (e.g., dc+sd-jwt or mso_mdoc) and its credential type (an SD-JWT VC vct value, an mdoc doctype, or W3C VC types). The [=user agent=] uses these to decide whether the [=instrument=] [=matches=] a Credential Query.
Display name and image
A human-readable name (e.g., "Visa ending in 1234") and optional thumbnail image, shown only in the payment sheet. They are never exposed to the merchant, and the [=user agent=] does not derive merchant-facing [=metadata=] from them.
Payment attributes
Optional values from which the [=user agent=] derives {{DigitalCredentialMetadata}}: the payment network, the instrument category, the funding type, and the account type. The [=user agent=] maps them as described in [[[#entropy-constraints]]].

A [=credential manager=] MAY include additional data in an [=instrument record=] for its own use. The [=user agent=] MUST NOT expose any of it to the merchant.

Metadata interface synchronization

Implementations are expected to have the platform [=credential manager=] pre-synchronize [=instrument records=] to the browser process, outside the context of any individual {{PaymentRequest}}, so that:

  • The [=user agent=] can populate the payment sheet from a local cache, without calling the [=credential manager=] for each {{PaymentRequest}}.
  • {{PaymentRequest/show()}} does not wait on external [=credential manager=] processes.
  • The time taken to show the payment sheet does not depend on how many [=credential managers=] or [=instruments=] the user has (see [[[#anti-enumeration-requirements]]]).

The synchronization mechanism and frequency are platform-specific. A [=user agent=] should not show an [=instrument=] whose record it has reason to believe is out of date (for example, a card the [=credential manager=] has since removed).

PaymentAuthorizeEvent interface

The {{PaymentAuthorizeEvent}} is fired when the user clicks "Pay" but before the Digital Credentials API is invoked. It allows the merchant to provide a fully-signed [=Presentation Request=] containing the final, negotiated amount. 

        [Exposed=Window, SecureContext]
        interface PaymentAuthorizeEvent : Event {
          constructor(DOMString type, PaymentAuthorizeEventInit eventInitDict);
          [SameObject] readonly attribute object total;
          undefined respondWith(
            Promise<DigitalCredentialSignedRequest> signedRequest,
            PaymentAuthorizeRespondOptions options
          );
          undefined decline(optional DOMString reason = "");
        };

        dictionary PaymentAuthorizeEventInit : EventInit {
          required PaymentCurrencyAmount total;
        };

        dictionary PaymentAuthorizeRespondOptions {
          required DOMString instrumentHandle;
        };

        dictionary DigitalCredentialSignedRequest {
          required DOMString protocol;
          required object data;
        };

`total` attribute

The {{PaymentAuthorizeEvent/total}} attribute represents the current payment total, as a frozen object with the members of a {{PaymentCurrencyAmount}}. The {{PaymentCurrencyAmount/currency}} member is an ISO 4217 currency code (e.g., "USD") and the {{PaymentCurrencyAmount/value}} member is a decimal string (e.g., "103.00").

When constructing the event, the [=user agent=] converts the {{PaymentAuthorizeEventInit/total}} member of the {{PaymentAuthorizeEventInit}} to a JavaScript object, freezes it, and returns that object from {{PaymentAuthorizeEvent/total}}. The attribute is typed as object because WebIDL does not permit dictionary-typed attributes; [[payment-handler]] uses the same approach for PaymentRequestEvent.total.

`respondWith()` method

When called, the {{PaymentAuthorizeEvent/respondWith(signedRequest, options)}} method MUST run the following steps:

  1. If [=this=]'s {{Event/isTrusted}} attribute is false, or [=this=]'s dispatch flag is unset, [=exception/throw=] an {{"InvalidStateError"}} {{DOMException}}.
  2. If [=this=].{{PaymentAuthorizeEvent/[[waitForUpdate]]}} is true, [=exception/throw=] an {{"InvalidStateError"}} {{DOMException}}.
  3. Set [=this=].{{PaymentAuthorizeEvent/[[waitForUpdate]]}} to true.
  4. Set [=this=].{{PaymentAuthorizeEvent/[[authorizationPromise]]}} to |signedRequest|.
  5. Set [=this=].{{PaymentAuthorizeEvent/[[instrumentHandle]]}} to |options|.{{PaymentAuthorizeRespondOptions/instrumentHandle}}.

{{PaymentAuthorizeEvent/respondWith()}} only records the merchant's response. The [=authorize a digital credential payment=] steps check the {{PaymentAuthorizeRespondOptions/instrumentHandle}} as soon as dispatch completes, then wait for |signedRequest| to settle and validate its value (see [[[#signed-request-validation]]]). Because of the dispatch flag check, {{PaymentAuthorizeEvent/respondWith()}} and {{PaymentAuthorizeEvent/decline()}} must be called synchronously during dispatch; calling either later throws.

The fulfillment value of |signedRequest| is a {{DigitalCredentialSignedRequest}}:

protocol member
The presentation protocol of the request, one of those listed in [[[#supported-presentation-protocols]]].
data member
The protocol-specific signed [=presentation request=]. The [=user agent=] forwards it unchanged as the Digital Credentials API's {{DigitalCredentialGetRequest/data}}. For OpenID4VP protocols it MUST carry a [=payment transaction data=] entry for the final total.

The {{DigitalCredentialMethodDetails/instrumentHandle}} is not a member of the signed request; it is passed separately via |options|.{{PaymentAuthorizeRespondOptions/instrumentHandle}}.

Apart from the checks in [[[#signed-request-validation]]], the [=user agent=] does not interpret {{DigitalCredentialSignedRequest/data}}; the merchant's signing layer and the [=credential manager=] are the parties that interpret it.

`decline()` method

When the {{PaymentAuthorizeEvent/decline(reason)}} method is called, the [=user agent=] MUST run the following steps:

  1. If [=this=]'s {{Event/isTrusted}} attribute is false, or [=this=]'s dispatch flag is unset, [=exception/throw=] an {{"InvalidStateError"}} {{DOMException}}.
  2. If [=this=].{{PaymentAuthorizeEvent/[[waitForUpdate]]}} is true, [=exception/throw=] an {{"InvalidStateError"}} {{DOMException}}.
  3. Set [=this=].{{PaymentAuthorizeEvent/[[waitForUpdate]]}} to true.
  4. If |reason| is the empty string, set |reason| to a [=user agent=]-defined default error message.
  5. Set [=this=].{{PaymentAuthorizeEvent/[[errorMessage]]}} to |reason|.

The [=authorize a digital credential payment=] steps then display |reason| in the payment sheet and return it to READY, so the user can retry.

The {{PaymentAuthorizeEvent/decline()}} method allows merchants to decline the authorization at dispatch time and display a reason to the user. Because both {{PaymentAuthorizeEvent/decline()}} and {{PaymentAuthorizeEvent/respondWith()}} must be called synchronously during event dispatch, {{PaymentAuthorizeEvent/decline()}} is the appropriate mechanism when the merchant already knows at dispatch time that it cannot proceed. The term decline matches the vocabulary used elsewhere in the payments ecosystem (ISO 8583, 3-D Secure) for an authorization rejection initiated by the merchant or processor.

There are two mechanisms for handling authorization failures, each suited to a different timing:

{{PaymentAuthorizeEvent/decline()}} — synchronous decline
Called during event dispatch when the merchant can determine immediately that authorization should not proceed. Provides a user-visible reason. The state returns to READY for retry.
{{Promise}} rejection via {{PaymentAuthorizeEvent/respondWith()}} — asynchronous abort
When the {{Promise}} passed to {{PaymentAuthorizeEvent/respondWith()}} rejects (e.g., due to a network error or server-side signing failure discovered after dispatch), the state also returns to READY for retry. The rejection reason is not displayed to the user; the [=user agent=] displays a generic error. 
          request.onpaymentauthorize = event => {
            if (fraudDetected) {
              // decline() must be called synchronously during dispatch.
              // Use it when the merchant already knows it cannot proceed.
              event.decline('Unable to process payment. Please try again.');
              return;
            }

            // For async operations, pass a promise to respondWith().
            // If the promise rejects, the payment sheet returns to READY.
            const signedRequestPromise = fetch('/api/sign-presentation-request', {
              method: 'POST',
              body: JSON.stringify({
                orderId,
                amount: event.total.value,
                currency: event.total.currency
              })
            }).then(r => {
              if (!r.ok) throw new Error('Signing failed');
              return r.json();
            });

            event.respondWith(signedRequestPromise, {
              instrumentHandle: currentInstrumentHandle
            });
          };

DigitalCredentialPaymentMethodData dictionary

The {{DigitalCredentialPaymentMethodData}} dictionary provides the additional data type for the `digital-credential-payment` [=payment method=]. It is provided by the merchant via the {{PaymentMethodData}}'s {{PaymentMethodData/data}} member when constructing a {{PaymentRequest}} object. 

        dictionary DigitalCredentialPaymentMethodData {
          required object credentialQuery;
        };
credentialQuery member
A DCQL query (Digital Credentials Query Language, [[OPENID4VP]] Section 6) describing the [=credentials=] the merchant accepts. The [=user agent=] reads it to decide which [=instruments=] to show (see [[[#credential-manager-discovery]]]). It is not itself a [=presentation request=] and is not forwarded to the [=credential manager=]. It carries no amount, so the merchant needs no placeholder total at construction time.

The [=user agent=] evaluates only each Credential Query's id, format, and the type constraint in its meta object (vct_values for dc+sd-jwt, doctype_value for mso_mdoc, type_values for the W3C Verifiable Credential formats, as defined in [[OPENID4VP]] Appendix B). It does not evaluate claims, claim_sets, trusted_authorities, or credential_sets, because it has no access to claim values. Those constraints are applied by the [=credential manager=] when it processes the final signed request.

When the {{PaymentRequest}} constructor converts {{PaymentMethodData/data}} to a {{DigitalCredentialPaymentMethodData}}, the [=user agent=] MUST also check that {{DigitalCredentialPaymentMethodData/credentialQuery}} has a non-empty credentials array in which every entry has a unique string id, a string format, and an object meta, and in which no entry sets require_cryptographic_holder_binding to false. If it does not, the constructor throws a {{TypeError}}.

Cryptographic holder binding is required because, without it, the [=presentation=] carries no proof bound to the request's nonce and can be replayed ([[OPENID4VP]] Sections 5.3 and 14.1.1). Because the final request's dcql_query must equal {{DigitalCredentialPaymentMethodData/credentialQuery}}, the requirement carries through to the request the [=credential manager=] processes.

For OpenID4VP protocols, the final signed request's dcql_query MUST equal {{DigitalCredentialPaymentMethodData/credentialQuery}}, so the [=instruments=] the user chose from are the ones the final request asks for (see [[[#signed-request-validation]]]). 

        const credentialQuery = {
          credentials: [
            {
              id: "card",
              format: "dc+sd-jwt",
              meta: { vct_values: ["https://credentials.example/payment-card"] }
            },
            {
              id: "bank",
              format: "mso_mdoc",
              meta: { doctype_value: "org.example.bank-account.1" }
            }
          ]
        };

DigitalCredentialMethodDetails dictionary

The {{DigitalCredentialMethodDetails}} dictionary is provided in the {{PaymentMethodChangeEvent}}'s {{PaymentMethodChangeEvent/methodDetails}} attribute, describing a user-selected [=instrument=]'s public properties. 

        dictionary DigitalCredentialMethodDetails {
          required DOMString type;
          required DOMString instrumentHandle;
          DigitalCredentialMetadata metadata;
        };

        dictionary DigitalCredentialMetadata {
          DOMString instrumentType;
          DOMString network;
          FundingType fundingType;
          AccountType accountType;
        };

        enum FundingType { "credit", "debit", "prepaid", "charge" };

        enum AccountType { "checking", "savings" };

The {{DigitalCredentialMetadata}} dictionary defines well-known keys for common [=metadata=] properties. All members are optional. [=User agents=] MUST NOT expose keys beyond those defined by this specification or by a future revision; uncoordinated extensions defeat the entropy and privacy constraints of this section by introducing high-cardinality fields that merchants could read. New keys may be added in subsequent revisions of this specification, subject to a privacy review against the same constraints.

type member
The id of the first Credential Query in {{DigitalCredentialPaymentMethodData/credentialQuery}}'s credentials that the selected [=instrument=] matches (for example, "card"). Because the merchant chose the value, it reveals only which of the merchant's own queries the [=instrument=] satisfies, not the [=credential=]'s actual type or issuer.
instrumentHandle member

An ephemeral, opaque token generated by the [=user agent=] that identifies the selected [=instrument=] for the duration of this transaction. To bind the [=presentation request=] to the [=instrument=] the user selected, the merchant passes this value as {{PaymentAuthorizeRespondOptions/instrumentHandle}} on the second argument to {{PaymentAuthorizeEvent/respondWith()}}. As soon as dispatch completes, the [=user agent=] checks the value and fails the request with a {{"SecurityError"}} if it does not match the value most recently issued for the current {{PaymentRequest}}. The merchant does not need to embed this value inside the signed [=presentation request=] (and should not, since it carries no merchant-asserted semantics).

The {{DigitalCredentialMethodDetails/instrumentHandle}} value:

  • MUST be a version 4 UUID [[RFC9562]].
  • MUST be unique per [=instrument=] selection event (a new value is generated each time the user selects or re-selects an [=instrument=]).
  • MUST NOT be correlated across sessions, origins, or transactions.
  • MUST NOT encode or reveal any information about the [=instrument=], [=credential=], or [=credential manager=].

The {{DigitalCredentialMethodDetails/instrumentHandle}} enables the [=user agent=] to verify that the merchant's authorization corresponds to the [=instrument=] the user selected, ensuring that the [=credential=] used for the Digital Credentials API invocation matches the [=instrument=] whose [=metadata=] informed the merchant's pricing decision. The [=user agent=] checks this binding by comparing the {{PaymentAuthorizeRespondOptions/instrumentHandle}} passed to {{PaymentAuthorizeEvent/respondWith()}} against its internally stored token before invoking the Digital Credentials API. Without this binding, a user could select a low-surcharge instrument to obtain favorable pricing, then have a different [=credential=] used during the authorization phase.

metadata member

A {{DigitalCredentialMetadata}} object containing non-PII [=metadata=].

The object MUST NOT contain:

  • Direct identifiers (full PAN, account number).
  • Personally identifiable information (cardholder name, address, email, phone).

Entropy constraints

The {{DigitalCredentialMetadata/fundingType}} and {{DigitalCredentialMetadata/accountType}} fields are constrained to the {{FundingType}} and {{AccountType}} enumerated values. The [=user agent=] MUST map the value the [=metadata interface=] provides to the corresponding enumeration value, and MUST omit the field if there is no corresponding value.

The remaining categorical fields are not enumerated by this specification. To limit fingerprinting risk, their values MUST be drawn from a finite, [=user agent=]-controlled set of short, lowercase ASCII identifiers. The [=user agent=] maintains the set internally. Where the [=metadata interface=] returns a value that is not in the [=user agent=]'s controlled set for that field, the [=user agent=] MUST omit the field rather than pass an unrecognized value through to the merchant. These fields are:

  • network: a payment network identifier (e.g., "visa", "mastercard").
  • instrumentType: an instrument category identifier (e.g., "card", "bank-transfer").

The [=user agent=]'s controlled set for each field MUST be finite and chosen so that each value has high entropy overlap across users; high-cardinality identifiers (e.g., exact issuer names, BIN ranges, card art identifiers) MUST NOT be admitted. The example values above are illustrative, not normative; see [[[#open-issues]]].

Because network and instrumentType remain [=user agent=]-controlled rather than enumerated by this specification, two conforming [=user agents=] MAY surface different identifier strings for the same underlying [=instrument=] property (e.g., one might use "americanexpress" where another uses "amex"). Merchants writing branching logic against these values should treat them as a best-effort hint rather than a stable contract. A registry is the intended long-term solution. {{FundingType}} and {{AccountType}} do not have this problem, since this specification enumerates them.

High-cardinality [=metadata=] fields (e.g., exact institution, card art identifier, BIN range) MUST NOT be exposed to merchants through {{PaymentMethodChangeEvent}} events.

[=User agents=] SHOULD monitor the cumulative [=metadata=] entropy exposed during a single {{PaymentRequest}} session and MAY suppress or coarsen [=metadata=] values if repeated [=instrument=] selections would exceed a reasonable entropy budget.

Obtaining metadata

To obtain the metadata for an [=instrument=] |instrument|, the [=user agent=] MUST run these steps, which return a {{DigitalCredentialMetadata}}:

  1. Let |metadata| be a new {{DigitalCredentialMetadata}}.
  2. For each of {{DigitalCredentialMetadata/network}}, {{DigitalCredentialMetadata/instrumentType}}, {{DigitalCredentialMetadata/fundingType}}, and {{DigitalCredentialMetadata/accountType}}: set that member on |metadata| to the value the [=metadata interface=] provides for |instrument|, applying the [[[#entropy-constraints]]] and omitting the member where those constraints require it.
  3. Return |metadata|.

There is deliberately no merchant-facing display label, because the merchant doesn't need one. While the payment sheet is open, the user sees the [=instrument record=]'s display name there. After authorization, the merchant can take the details it needs for receipts and order records from the claims it requested in the [=presentation=].

protocol member
The presentation protocol of the response, which is the protocol of the merchant's signed request.
data member
The data of the DigitalCredential the [=credential manager=] returned, in the form the protocol defines (for OpenID4VP, the Authorization Response, Appendix A.4). It carries a [=presentation=] of the [=credential=] backing the selected [=instrument=] only (see [[[#wallet-requirements]]]).

Processing model

This section extends the Payment Request processing model for the `digital-credential-payment` [=payment method=].

Steps to check if a payment can be made

The `digital-credential-payment` [=payment method=] defines its steps to check if a payment can be made, which [[payment-request]] runs while deciding whether the method appears, as follows:

  1. If the [=user agent=] supports the `digital-credential-payment` [=payment method=] and its [=metadata interface=] is available, return true.
  2. Otherwise, return false.

These steps depend only on [=user agent=] and platform support, never on whether the user holds a matching [=instrument=]. Returning false because no [=instrument=] matches would remove the method from an otherwise-empty Payment Sheet and cause {{PaymentRequest/show()}} to reject with a {{"NotSupportedError"}}, which a merchant could observe to learn the user has no matching [=instrument=]. The method therefore appears whenever it is supported (see [[[#no-matching-instrument-behavior]]]).

Credential manager discovery

When the [=user agent=] presents the Payment Request UI for the `digital-credential-payment` [=payment method=], it populates the payment sheet by discovering available [=credential managers=] as follows. Discovery populates the sheet only; it does not decide whether the method appears.

An [=instrument=] |instrument| matches a DCQL Credential Query |query| if the [=metadata interface=] reports, for the [=credential=] backing |instrument|, a credential format equal to |query|'s format and a credential type that satisfies the type constraint in |query|'s meta object for that format, as defined in [[OPENID4VP]] Appendix B.

  1. Let |data| be the {{DigitalCredentialPaymentMethodData}} the merchant supplied for the `digital-credential-payment` [=payment method=].
  2. Let |queries| be the credentials array of |data|.{{DigitalCredentialPaymentMethodData/credentialQuery}}.
  3. Let |credentialManagers| be a [=list=] of the [=credential managers=], discovered using platform-specific mechanisms, that support `digital-credential-payment`.
  4. Let |instruments| be an empty [=list=].
  5. [=list/For each=] |credentialManager| of |credentialManagers|:
    1. [=list/For each=] payment [=instrument=] |instrument| that |credentialManager| exposes through the [=metadata interface=]: if |instrument| [=matches=] at least one entry of |queries|, [=list/append=] |instrument| to |instruments|.
  6. Incorporate |instruments| into the Payment Request UI.

Discovery surfaces [=instruments=] to the payment sheet using information the [=user agent=] holds internally; it does not derive merchant-facing [=metadata=]. No [=instrument=] information is exposed to the merchant until the user explicitly selects an [=instrument=], at which point only the selected [=instrument=]'s [=metadata=], obtained per [=obtain the metadata=], is provided via {{PaymentMethodChangeEvent}}.

The [=metadata interface=] invocation:

  • MUST NOT request a credential from the [=credential manager=] (i.e., MUST NOT trigger the Digital Credentials API's request-a-credential algorithm).
  • MUST NOT perform any cryptographic signing.
  • MUST NOT retrieve or expose sensitive [=credential=] data beyond display-friendly labels and non-PII [=metadata=].

No matching instrument behavior

If no [=instruments=] in any discovered [=credential manager=] [=match=] a Credential Query in {{DigitalCredentialPaymentMethodData/credentialQuery}}:

  • If the payment sheet shows at least one other [=payment method=] from the same {{PaymentRequest}}, the [=user agent=] MAY omit the `digital-credential-payment` option. The user pays with another method or cancels, and {{PaymentRequest/show()}} behaves exactly as it would for a user who had matching [=instruments=] and chose not to use them.
  • Otherwise, the `digital-credential-payment` method MUST still appear and its payment sheet MUST still be presented, showing no available [=instruments=]. The user can only cancel, which rejects {{PaymentRequest/show()}} with an {{"AbortError"}}, exactly as for a user who had matching [=instruments=] but declined.

When it is the only method, the `digital-credential-payment` method MUST NOT remove itself from the Payment Sheet because no [=instrument=] matches. Doing so would leave an otherwise-empty sheet and cause {{PaymentRequest/show()}} to reject with a {{"NotSupportedError"}}, which a merchant could observe to detect that the user holds no matching [=instrument=]. Collapsing the no-match case to the same {{"AbortError"}} as a decline ensures merchants cannot distinguish the two, preserving this specification's anti-enumeration guarantees. Omitting the option when other methods remain reveals nothing, because the merchant observes the same outcomes either way.

The empty payment sheet is an opportunity for the [=user agent=] to explain why no [=instrument=] is available (for example, that the merchant accepts payment [=credentials=] the user doesn't hold yet) and how they might add one to a [=credential manager=]. This guidance is shown only in the payment sheet and must not change what the merchant observes: if the user leaves the sheet to follow it, {{PaymentRequest/show()}} rejects with the same {{"AbortError"}} as any other cancellation. How [=credentials=] are added is outside the scope of this specification.

Instrument selection

Instrument selection occurs while the user interacts with the `digital-credential-payment` [=payment handler=]: that is, after {{PaymentRequest/show()}} has presented the payment UI and the user has selected this [=payment handler=]. Selecting among [=instruments=] happens within that handler.

When the user selects a `digital-credential-payment` [=instrument=] |instrument|, the [=user agent=] MUST run the following steps:

  1. Let |request| be the {{PaymentRequest}} the user is interacting with.
  2. Let |instrumentHandle| be a newly generated version 4 UUID [[RFC9562]], in its string representation.
  3. Set |request|.{{PaymentRequest/[[selectedInstrument]]}} to a [=struct=] whose `handle` is |instrumentHandle| and whose `instrument` is |instrument|, replacing any previous value.
  4. Let |metadata| be the result of [=obtaining the metadata=] for |instrument|.
  5. Let |methodDetails| be a {{DigitalCredentialMethodDetails}} dictionary with:
    1. {{DigitalCredentialMethodDetails/type}} set to the id of the first Credential Query in |request|'s {{DigitalCredentialPaymentMethodData/credentialQuery}} that |instrument| [=matches=].
    2. {{DigitalCredentialMethodDetails/instrumentHandle}} set to |instrumentHandle|.
    3. If |metadata| has at least one member set, {{DigitalCredentialMethodDetails/metadata}} set to |metadata|.
  6. Run the [=payment handler/payment method changed algorithm=] with |methodDetails| and "digital-credential-payment" as the |methodName|.

Anti-enumeration requirements

The {{PaymentMethodChangeEvent}} MUST NOT be fired until the user has explicitly interacted with the Payment Request UI by selecting a payment [=instrument=]. [=Metadata=] MUST NOT be exposed to the merchant prior to user interaction.

The selected [=instrument=]'s [=metadata=] reaches the merchant when the user selects it, before the user confirms payment, because the merchant may need it to adjust the price. A user who selects an [=instrument=] and then cancels has still disclosed that [=instrument=]'s [=metadata=], and selecting several [=instruments=] in turn discloses each of them (subject to the entropy budget in [[[#entropy-constraints]]]).

[=User agents=] MUST ensure that merchants cannot infer the number of available [=instruments=] by observing the presence, absence, or timing of {{PaymentMethodChangeEvent}} events. Specifically:

  • The [=user agent=] MUST NOT expose the full set of available [=credential=] types or [=instrument=] count to the merchant.
  • Only the currently selected [=instrument=]'s [=metadata=] is revealed via {{PaymentMethodChangeEvent}}.
  • [=User agents=] MUST NOT fire {{PaymentMethodChangeEvent}} events in a pattern that reveals [=instrument=] count.
  • [=User agents=] MUST NOT expose whether the user browsed other [=instruments=] before selecting one.
  • {{PaymentRequest/canMakePayment()}} MUST NOT reveal the absence of matching [=credentials=].
  • [=User agents=] MUST ensure that the latency of displaying the Payment Request UI and firing events does not reveal the number of available [=credential managers=] or [=credentials=] to timing side-channels.

Shipping and billing addresses

A merchant collects shipping and contact information through [[payment-request]]'s {{PaymentOptions/requestShipping}}, {{PaymentOptions/requestPayerName}}, {{PaymentOptions/requestPayerEmail}}, and {{PaymentOptions/requestPayerPhone}} options. The `digital-credential-payment` [=payment method=] adds nothing here: shipping address and shipping option selection, the events they fire, and the resulting {{PaymentResponse/shippingAddress}} are handled entirely by [[payment-request]]. Whatever total the merchant sets through {{PaymentRequestUpdateEvent/updateWith()}} in response is the total this [=payment method=] authorizes.

This [=payment method=] does not surface an [=instrument=]'s billing address to the merchant, so {{PaymentOptions/requestBillingAddress}} has no effect for it: no address crosses the merchant boundary through {{DigitalCredentialMethodDetails}}, consistent with this specification's requirement that the [=user agent=] not expose PII via that dictionary. A merchant that needs a billing or other identity-bound address requests it as a claim in its {{DigitalCredentialPaymentMethodData/credentialQuery}} (and so in the final signed request); it is then returned in the [=presentation=]. See [[[#data-precedence-for-address-and-contact-information]]].

Address claims are returned only from the [=credential=] backing the selected [=instrument=], because this [=payment method=] presents exactly one [=credential=] per payment. It does not support paying with one [=credential=] while taking an address from another, for example paying from a bank account while taking the billing address from an identity document. A future version of this specification may support this (see "Multiple Credentials" in [[[#open-issues]]]). Until then, a merchant can collect the address through [[payment-request]]'s existing options.

Authorizing a payment

When the user activates the Pay affordance while a `digital-credential-payment` [=instrument=] is selected, the [=user agent=] MUST run the [=authorize a digital credential payment=] steps for the {{PaymentRequest}} the user is interacting with. These steps run before the user accepts the payment request algorithm of [[payment-request]]; only when they succeed does the [=user agent=] run that algorithm, whose call to this [=payment method=]'s steps to respond to a payment request returns the authorized result.

While the [=authorize a digital credential payment=] steps are running, the [=user agent=] MUST NOT let the user select a different [=instrument=]. The steps check the merchant's {{PaymentAuthorizeRespondOptions/instrumentHandle}} against the selection before waiting for the signed request, and then invoke the [=credential manager=] for that same [=instrument=]. A selection made during the wait would otherwise send a request priced for one [=instrument=] to another.

[[payment-request]] does not define a point, between the user activating Pay and the request being accepted, at which a [=payment method=] can run asynchronous steps, return the payment sheet to an earlier state, or fail the request with a method-specific error. This specification assumes one. It needs coordination with the Web Payments Working Group, either as a generic hook in [[payment-request]] or as agreement that payment methods may define such steps.

The {{PaymentAuthorizeEvent}} fires only when the user pays with the `digital-credential-payment` [=payment method=]. The {{PaymentRequest/onpaymentauthorize}} attribute is still present on every {{PaymentRequest}}, so merchants can feature-detect support. If [[payment-request]] later adds a general authorization hook for all payment methods, this specification will move to it.

To return to ready with a message |message|: display |message| in the payment sheet's error UI, convey it to assistive technologies, and re-enable the Pay affordance. The request stays "interactive" and {{PaymentRequest/show()}} stays pending; activating Pay again runs the [=authorize a digital credential payment=] steps again, with a new {{PaymentAuthorizeEvent}}.

To fail the payment request |request| with an error |error|:

  1. Set |request|'s [[\state]] to "closed".
  2. If |request|'s [[\response]] is not null (a {{PaymentResponse/retry()}} is in progress), [=reject=] that response's [[\retryPromise]] with |error|. Otherwise, [=reject=] |request|'s [[\acceptPromise]] (the promise returned by {{PaymentRequest/show()}}) with |error|.
  3. Close down the payment UI.

To handle a cancelled ceremony: depending on platform conventions, either [=return to ready=] with a [=user agent=]-defined message, or run the user aborts the payment request algorithm, which rejects {{PaymentRequest/show()}} with an {{"AbortError"}}.

To authorize a digital credential payment for a {{PaymentRequest}} |request|, run the following steps in parallel. Steps that fire events, settle promises, or otherwise touch the page run in tasks queued on the user interaction task source.

  1. Let |total| be |request|'s current payment total (a {{PaymentCurrencyAmount}}).
  2. Let |authorizeEvent| be the result of constructing a new {{PaymentAuthorizeEvent}} with type "paymentauthorize" and a {{PaymentAuthorizeEventInit}} whose {{PaymentAuthorizeEventInit/total}} is |total|.
  3. Fire an event named "paymentauthorize" at |request| using |authorizeEvent|.
  4. If |authorizeEvent|.{{PaymentAuthorizeEvent/[[errorMessage]]}} is not null (the merchant called {{PaymentAuthorizeEvent/decline()}}), [=return to ready=] with that message and abort these steps.
  5. If |authorizeEvent|.{{PaymentAuthorizeEvent/[[authorizationPromise]]}} is null (the merchant called neither method during dispatch), [=fail the payment request=] |request| with an {{"InvalidStateError"}} {{DOMException}} and abort these steps.
  6. Let |selection| be |request|.{{PaymentRequest/[[selectedInstrument]]}}. If |selection| is null, or |authorizeEvent|.{{PaymentAuthorizeEvent/[[instrumentHandle]]}} does not equal |selection|'s handle, [=fail the payment request=] |request| with a {{"SecurityError"}} {{DOMException}} and abort these steps. Otherwise, let |selectedInstrument| be |selection|'s instrument. The rest of these steps use |selectedInstrument|, not whatever is selected later.
  7. Let |timeoutMs| be the [=user agent=]'s authorization timeout in milliseconds. The [=user agent=] MUST enforce a finite authorization timeout; |timeoutMs| SHOULD be no greater than 30000 (30 seconds), and MAY be shorter. The merchant cannot observe or extend |timeoutMs|.
  8. Wait until either |authorizeEvent|.{{PaymentAuthorizeEvent/[[authorizationPromise]]}} settles or |timeoutMs| milliseconds have elapsed:
    1. If the timeout elapses first, [=return to ready=] with a [=user agent=]-defined timeout message and abort these steps. The promise's later settlement is ignored.
    2. If the promise was rejected, [=return to ready=] with a [=user agent=]-defined generic error message and abort these steps. The rejection reason is not shown to the user.
  9. Let |signedRequest| be the result of converting the promise's fulfillment value to a {{DigitalCredentialSignedRequest}}. If this throws, [=fail the payment request=] |request| with a {{TypeError}} and abort these steps.
  10. Let |result| be the result of [=validating the signed request=] |signedRequest| for |request| and |total|. If |result| is an error, [=fail the payment request=] |request| with |result| and abort these steps.
  11. Let |dcOptions| be a {{CredentialRequestOptions}} dictionary with {{CredentialRequestOptions/digital}} set to a {{DigitalCredentialRequestOptions}} dictionary whose {{DigitalCredentialRequestOptions/requests}} member contains a single {{DigitalCredentialGetRequest}} whose {{DigitalCredentialGetRequest/protocol}} is |signedRequest|.{{DigitalCredentialSignedRequest/protocol}} and whose {{DigitalCredentialGetRequest/data}} is |signedRequest|.{{DigitalCredentialSignedRequest/data}}, unchanged.
  12. The [=user agent=] MUST internally constrain the Digital Credentials API invocation to the [=credential=] backing |selectedInstrument|, and MUST convey |total| to the [=credential manager=] alongside the request. The mechanism (e.g., an opaque credential-manager-scoped handle passed out-of-band) is implementation-specific and MUST NOT be observable by the merchant.
  13. Let |dcPromise| be the result of executing the request a credential algorithm with |dcOptions|. The page does not hold transient activation at this point; see [[[#wallet-invocation-and-user-activation]]].
  14. Wait for |dcPromise| to settle:
    1. If |dcPromise| was rejected because the user cancelled the [=credential manager=]'s ceremony, [=handle a cancelled ceremony=] and abort these steps.
    2. If |dcPromise| was rejected for any other reason, [=fail the payment request=] |request| with the rejection reason and abort these steps.
  15. Let |credential| be the fulfillment value of |dcPromise|.
  16. If |signedRequest|.{{DigitalCredentialSignedRequest/protocol}} is an OpenID4VP protocol and |credential|'s data has an error member (an OpenID4VP error response, [[OPENID4VP]] Appendix A.4):
    1. If the error is "access_denied", [=handle a cancelled ceremony=] and abort these steps.
    2. Otherwise, [=fail the payment request=] |request| with an {{"OperationError"}} {{DOMException}} and abort these steps. The [=user agent=] MUST NOT expose the error code to the merchant.
  17. Set |request|.{{PaymentRequest/[[authorizedDetails]]}} to a new {{DigitalCredentialPaymentResponse}} whose {{DigitalCredentialPaymentResponse/protocol}} is |signedRequest|.{{DigitalCredentialSignedRequest/protocol}} and whose {{DigitalCredentialPaymentResponse/data}} is |credential|'s data.
  18. Run the user accepts the payment request algorithm for |request|.

OpenID4VP returns wallet errors as a successful Digital Credentials API response, and warns that an error code can reveal which [=credentials=] the user holds ([[OPENID4VP]] Section 15.9.2). Treating access_denied (which covers the user declining, having no matching [=credential=], and failing to authenticate) like a cancellation, and collapsing every other code to one {{"OperationError"}}, keeps these cases as indistinguishable as the rest of this specification's anti-enumeration design.

Steps to respond to a payment request

The `digital-credential-payment` [=payment method=]'s steps to respond to a payment request, given a {{PaymentRequest}} |request|, are:

  1. Return |request|.{{PaymentRequest/[[authorizedDetails]]}}.

[[payment-request]]'s user accepts the payment request algorithm only runs once the [=authorize a digital credential payment=] steps have succeeded, so the value is never null here. That algorithm then builds the {{PaymentResponse}} as usual, including {{PaymentResponse/methodName}}, shipping and payer details, and {{PaymentResponse/retry()}} handling.

Optimistic signing

In scenarios where the payment total becomes stable before the user clicks "Pay" (e.g., after shipping selection is finalized), merchants MAY use optimistic signing to reduce authorization latency.

With [=optimistic signing=], the merchant:

  1. Generates and caches a signed [=presentation request=] during the {{PaymentMethodChangeEvent}} handler when the amount is known to be final.
  2. Stores this pre-signed request for the current [=instrument=] and amount combination.
  3. In the {{PaymentAuthorizeEvent}} handler, checks if a valid pre-signed request exists for the current total.
  4. If a valid pre-signed request exists, immediately calls {{PaymentAuthorizeEvent/respondWith()}} without a network round-trip. 
          let preSigned = null; // { signedRequest, amount, instrumentHandle }
          let currentInstrumentHandle = null;

          request.onpaymentmethodchange = async event => {
            // Capture this selection's handle before any await, so a
            // later re-selection cannot be confused with this one.
            const instrumentHandle = event.methodDetails.instrumentHandle;
            currentInstrumentHandle = instrumentHandle;
            preSigned = null;

            const updated = calculatePriceUpdate(event.methodDetails);
            event.updateWith(updated);

            // If amount is now stable, pre-sign the request. The
            // signing endpoint builds the request from server-side
            // order state and creates a fresh random nonce (see "Replay
            // attack prevention"); the client never generates the nonce.
            if (isAmountStable()) {
              const r = await fetch('/api/sign-presentation-request', {
                method: 'POST',
                body: JSON.stringify({
                  orderId,
                  amount: updated.total.amount.value,
                  currency: updated.total.amount.currency
                })
              });
              // Keep the result only if the user has not re-selected
              // an instrument while the request was in flight.
              if (r.ok && instrumentHandle === currentInstrumentHandle) {
                preSigned = {
                  signedRequest: await r.json(),
                  amount: updated.total.amount.value,
                  instrumentHandle
                };
              }
            }
          };

          request.onpaymentauthorize = event => {
            // respondWith() MUST be called synchronously during dispatch.
            if (preSigned &&
                preSigned.amount === event.total.value &&
                preSigned.instrumentHandle === currentInstrumentHandle) {
              // Use the pre-signed request: amount and instrument match.
              const { signedRequest, instrumentHandle } = preSigned;
              // Discard after use so retries obtain a fresh nonce
              preSigned = null;
              event.respondWith(Promise.resolve(signedRequest), {
                instrumentHandle
              });
              return;
            }

            // Fall back to on-demand signing via a promise. The
            // signing endpoint creates a fresh nonce server-side.
            const signedRequestPromise = fetch('/api/sign-presentation-request', {
              method: 'POST',
              body: JSON.stringify({
                orderId,
                amount: event.total.value,
                currency: event.total.currency
              })
            }).then(r => {
              if (!r.ok) throw new Error('Signing failed');
              return r.json();
            });

            event.respondWith(signedRequestPromise, {
              instrumentHandle: currentInstrumentHandle
            });
          };

When using [=optimistic signing=], merchants need to ensure that their server still accepts the pre-signed request's nonce (for example, that the session it was issued for is still valid) and that the amount still matches at authorization time. If the user re-selects an [=instrument=] after pre-signing (generating a new {{DigitalCredentialMethodDetails/instrumentHandle}}), the pre-signed request is invalidated, and the merchant obtains a fresh signed request before passing the new {{DigitalCredentialMethodDetails/instrumentHandle}} to {{PaymentAuthorizeEvent/respondWith()}}. If authorization fails and the user retries (e.g., after a [=credential manager=] authentication failure or network error), the pre-signed request is discarded and a fresh signed request with a new nonce is obtained for the retry attempt; reusing a nonce across attempts risks rejection by the merchant's backend, which is expected to refuse previously-seen nonces.

Payment transaction data

A payment transaction data entry is an OpenID4VP transaction_data entry ([[OPENID4VP]] Section 8.4) that binds the final total into the [=presentation=]. When decoded, it is a JSON object with the following members:

type
The string "digital-credential-payment".
credential_ids
As defined by [[OPENID4VP]]: the ids of the Credential Queries in the request's dcql_query whose [=credentials=] can authorize this payment.
amount
The final total, as an object with currency and value members that follow the same rules as {{PaymentCurrencyAmount/currency}} and {{PaymentCurrencyAmount/value}}.

A [=credential manager=] that receives a request with a [=payment transaction data=] entry MUST show the amount to the user before authenticating them, and MUST bind the entry into the [=presentation=] as [[OPENID4VP]] requires for the credential format: for dc+sd-jwt, by including its hash in transaction_data_hashes in the Key Binding JWT (Appendix B.3.3.1); for mso_mdoc, as a DeviceSigned data element (Appendix B.2.1). The merchant's server can then check that the user authorized exactly this amount.

Signed request validation

The [=user agent=] checks a small number of properties of the merchant's {{DigitalCredentialSignedRequest}} before forwarding it. For OpenID4VP protocols, the request object is a JWS whose payload is base64url-encoded JSON ([[OPENID4VP]] Appendix A.3.2), so the [=user agent=] can read it without the merchant's key and without parsing any credential format. It does not verify the signature; the [=credential manager=] does.

To validate the signed request |signedRequest| for a {{PaymentRequest}} |request| and a total |total|, run the following steps. They return either success or an error.

  1. Let |protocol| be |signedRequest|.{{DigitalCredentialSignedRequest/protocol}} and |data| be |signedRequest|.{{DigitalCredentialSignedRequest/data}}.
  2. If |protocol| is not one of the protocols listed in [[[#supported-presentation-protocols]]], or the [=user agent=] does not support it as a Digital Credentials API presentation protocol, return a {{TypeError}}. Unsigned OpenID4VP requests are rejected here.
  3. If |protocol| is "org-iso-mdoc", return success. The [=user agent=] does not decode these requests; the [=credential manager=] checks the amount against the total the [=user agent=] conveys (see [[[#wallet-requirements]]]).
  4. Let |payload| be:
    • For "openid4vp-v1-signed": the payload part of |data|'s request member, which MUST be a string in JWS Compact Serialization.
    • For "openid4vp-v1-multisigned": |data|'s payload member, which MUST be a string (JWS JSON Serialization).
    If that member is missing or not a string, return a {{TypeError}}.
  5. Let |params| be the result of base64url-decoding |payload| and parsing the result as JSON. If either fails, or |params| is not a JSON object, return a {{TypeError}}.
  6. Let |entries| be the [=list=] of entries of |params|'s transaction_data array, each base64url-decoded and parsed as JSON, whose type is "digital-credential-payment". If transaction_data is missing or malformed, or |entries| does not contain exactly one item, return a {{TypeError}}.
  7. Let |amount| be the amount member of |entries|[0]. If |amount| is not an object with string currency and value members, return a {{TypeError}}.
  8. If |amount|'s value is not identical to |total|'s {{PaymentCurrencyAmount/value}}, or |amount|'s currency is not an ASCII case-insensitive match for |total|'s {{PaymentCurrencyAmount/currency}}, return a {{"SecurityError"}} {{DOMException}}.
  9. If |params|'s dcql_query is not structurally equal to |request|'s {{DigitalCredentialPaymentMethodData/credentialQuery}} (the same members and array elements, recursively, with identical primitive values; member order is not significant), return a {{"SecurityError"}} {{DOMException}}.
  10. Return success.

The [=user agent=] does not check the request's signature, nonce, expected_origins, or claims. Those are checked by the [=credential manager=] (see [[[#wallet-requirements]]]) and by the merchant's server.

The [=credential manager=] verifies the signature over the same payload the [=user agent=] decoded. A request that passes these checks therefore carries, under the merchant's signature, the total the user saw in the payment sheet, and asks for the same [=credentials=] the user chose from. A failed check closes the request rather than returning to READY, because it indicates a merchant bug or a tampered request rather than a transient failure.

The {{DigitalCredentialMethodDetails/instrumentHandle}} is not part of the signed request: it is supplied via {{PaymentAuthorizeRespondOptions/instrumentHandle}} on the second argument to {{PaymentAuthorizeEvent/respondWith()}}, and checked against the handle of {{PaymentRequest/[[selectedInstrument]]}} as soon as dispatch completes.

The [=user agent=] cannot read the amount of an "org-iso-mdoc" request, and ISO/IEC 18013-7 does not yet define where such a request carries a signed transaction amount. For that protocol, the only amount check is the [=credential manager=]'s comparison with the total the [=user agent=] conveys.

The payment sheet may show the claims requested in {{DigitalCredentialPaymentMethodData/credentialQuery}}, and the [=user agent=] checks that the final request asks for the same [=credentials=]. The [=credential manager=]'s ceremony, which shows the claims about to be disclosed before the user authenticates, remains the authoritative consent moment for what is released.

State diagram

The following diagram illustrates the state transitions for this [=payment method=]. States in bold represent user-visible UI states; states in italics represent internal processing states.

Prose summary: The payment flow begins in the CREATED state. Calling show() transitions to the ACTIVE state (payment UI displayed). When the user selects an [=instrument=], the state moves to INSTRUMENT SELECTED, which triggers a paymentmethodchange event and enters AWAITING PRICE UPDATE. After the merchant calls updateWith(), the state becomes READY (Pay button enabled). When the user clicks Pay, the state becomes AUTHORIZING (the paymentauthorize event fires). After the merchant's signed request arrives and passes validation, AUTHENTICATING invokes the Digital Credentials API and [=credential manager=] authentication. A successful [=presentation=] transitions to CLOSED (resolved). A merchant-side failure (a decline, a rejected promise, or a timeout) returns to READY so the user can retry; a failed validation check, a missing response, or a [=credential manager=] error closes the request (rejected). The user can cancel at any point.

READY Price negotiation complete; Pay button enabled.
AUTHORIZING User clicked Pay; {{PaymentAuthorizeEvent}} fired; awaiting merchant {{PaymentAuthorizeEvent/respondWith()}}. The [=user agent=] MUST display a progress indicator in the payment sheet for the duration of this state, since the merchant's signing round-trip can take several seconds and the timeout window is up to 30 seconds. The selected [=instrument=] cannot be changed in this state (see [[[#authorizing-a-payment]]]).
AUTHENTICATING Digital Credentials API invoked; [=credential manager=] performing user authentication and [=presentation=] creation.
CLOSED Terminal state; {{PaymentRequest/show()}} {{Promise}} resolved or rejected.

Failure transition notes

The following clarifies state transitions on failure:

decline(), a rejected promise, or a timeout
If {{PaymentAuthorizeEvent/decline()}} is called, the {{Promise}} passed to {{PaymentAuthorizeEvent/respondWith()}} rejects, or the authorization timeout elapses, the state returns to READY and {{PaymentRequest/show()}} stays pending. The payment sheet displays the merchant's decline reason, or a [=user agent=]-defined message, and the user can retry by clicking "Pay" again, which fires a new {{PaymentAuthorizeEvent}}.
Validation failure or no response
If the merchant calls neither method during dispatch, the state transitions to CLOSED and {{PaymentRequest/show()}} is rejected with an {{"InvalidStateError"}} {{DOMException}}. If the {{PaymentAuthorizeRespondOptions/instrumentHandle}} does not match, or the signed request fails [[[#signed-request-validation]]], the state also transitions to CLOSED. {{PaymentRequest/show()}} is then rejected with a {{TypeError}} for a malformed or unsupported request, or with a {{"SecurityError"}} {{DOMException}} for a mismatch (instrument handle, amount, or credential query). These indicate a merchant bug or a tampered request, so there is no retry.
User cancellation during authentication
If the user cancels during the AUTHENTICATING state (e.g., dismisses the [=credential manager=] authentication prompt), the [=user agent=] MAY return to READY to allow retry, or MAY transition to CLOSED depending on platform conventions.

Relationship to Payment Request internal state

The states defined above are sub-states within the [[payment-request]] state machine. Specifically, every sub-state listed in the table — except CREATED and CLOSED — is a sub-state of the "interactive" value of {{PaymentRequest}}'s [[\state]] internal slot. CREATED corresponds to "created" and CLOSED corresponds to "closed".

The AWAITING PRICE UPDATE sub-state corresponds to the [[\updating]] internal slot being true; transitions out of AWAITING PRICE UPDATE happen when the {{PaymentRequestUpdateEvent/updateWith()}} {{Promise}} settles, at which point [[\updating]] returns to false and this specification's state machine moves to READY.

The {{PaymentRequest}} methods defined by [[payment-request]] interact with this specification's sub-states as follows:

{{PaymentRequest/abort()}}
MAY be called from any sub-state of "interactive". If [[\state]] transitions to "closed" while this specification's state machine is in any sub-state other than CLOSED, the [=user agent=] MUST stop waiting for the merchant's signed request (ignoring its later settlement) and abandon any in-flight credential manager request started for this {{PaymentRequest}}. The state machine moves directly to CLOSED.
{{PaymentResponse/retry()}}
When the [[payment-request]] algorithm transitions [[\state]] from "closed" back to "interactive" in response to {{PaymentResponse/retry()}}, this specification's state machine re-enters READY. The merchant MAY receive a new {{PaymentMethodChangeEvent}} (re-running the price-negotiation hook) before the user clicks "Pay" again. The [=user agent=] sets {{PaymentRequest/[[authorizedDetails]]}} to null, and the previously issued {{DigitalCredentialMethodDetails/instrumentHandle}} MUST be treated as stale; a new one is issued on the next [=instrument=] selection.
{{PaymentResponse/complete()}}
Has its standard [[payment-request]] semantics — it does not interact with this specification's sub-states because complete() is only callable after [[\state]] has reached "closed" successfully (i.e., once this specification's state machine has reached CLOSED via the success path).

Implementers should treat AUTHORIZING and AUTHENTICATING as transient sub-states that are not directly observable by the merchant — they exist to give a precise home for the timeout, signed-request-validation, and credential-manager-authentication failure modes. From the merchant's perspective, the only observable state changes are the events ({{PaymentMethodChangeEvent}}, {{PaymentAuthorizeEvent}}) and the eventual settlement of {{PaymentRequest/show()}}.

Supported presentation protocols

The merchant's final signed request MUST use one of the following Digital Credentials API presentation protocols:

  • "openid4vp-v1-signed" and "openid4vp-v1-multisigned" ([[OPENID4VP]] Appendix A). These carry SD-JWT VC, mdoc (mso_mdoc), and W3C Verifiable Credential presentations, and are validated as described in [[[#signed-request-validation]]].
  • "org-iso-mdoc" (ISO/IEC 18013-7). The [=credential manager=] MUST require reader authentication for these requests (see [[[#wallet-requirements]]]). The [=user agent=] does not decode them.

Unsigned OpenID4VP requests ("openid4vp-v1-unsigned") are not supported: the merchant's signature is what stops a script running at the merchant origin from substituting its own response-encryption key or transaction data (see [[[#defence-against-merchant-origin-xss]]]). A request that uses any other protocol, or one the [=user agent=] does not support, fails [[[#signed-request-validation]]] with a {{TypeError}} and is not forwarded to the Digital Credentials API.

Handling events

Handling paymentmethodchange

The merchant's {{PaymentMethodChangeEvent}} handler can read {{PaymentMethodChangeEvent/methodDetails}} to obtain the {{DigitalCredentialMethodDetails}} and adjust payment details accordingly. 

          let currentInstrumentHandle = null;

          request.onpaymentmethodchange = event => {
            // Capture the instrumentHandle for use during authorization
            currentInstrumentHandle = event.methodDetails.instrumentHandle;

            // Deep-copy the base details: a shallow copy would share
            // details.total.amount, so a discount applied for one
            // selection would leak into every later selection.
            const updated = structuredClone(details);

            // methodDetails.type is the id of the merchant's own
            // Credential Query that the instrument matched.
            if (event.methodDetails.type === 'bank') {
              updated.total.amount.value = '98.00';
              updated.displayItems = [
                { label: 'Subtotal', amount: { currency: 'USD', value: '100.00' } },
                { label: 'Bank Transfer Discount', amount: { currency: 'USD', value: '-2.00' } }
              ];
            }

            event.updateWith(updated);
          };

If the merchant determines it cannot accept the selected [=instrument=], the merchant MAY call {{PaymentRequestUpdateEvent/updateWith()}} with an updated {{PaymentDetailsUpdate}} that sets an error message via the {{PaymentDetailsUpdate/error}} field.

When the merchant's {{PaymentRequestUpdateEvent/updateWith()}} changes the displayed total, the [=user agent=] MUST conspicuously surface the change to the user before the user can authorize the payment. Conformant surfacing MUST satisfy all of the following:

  • The new total MUST be visually distinguished from the previous total (for example, by a transient highlight, a colour change, or an explicit delta line item) at the moment the change is rendered.
  • The Pay affordance MUST be temporarily unavailable immediately after the change is rendered, for a duration the [=user agent=] determines is sufficient for the user to register the change before authorizing.
  • If the change increases the total, the surfacing MUST remain visible until the user re-engages the Pay affordance after it becomes available again.

This is intended to defend against "checkout surprise" attacks in which a merchant materially raises the price between sheet display and authorization.

Data precedence for address and contact information

When a [=presentation=] includes address or contact claims (e.g., for identity verification purposes), merchants may receive similar data from two sources:

Payment Request shipping/contact data
Collected via the Payment Request API's {{PaymentOptions/requestShipping}}, {{PaymentOptions/requestPayerEmail}}, {{PaymentOptions/requestPayerPhone}}, and {{PaymentOptions/requestPayerName}} options. This data is intended for checkout orchestration: calculating taxes, determining shipping costs, and order fulfillment.
Presentation claims
Address or contact claims embedded in the [=presentation=] as requested in the merchant's {{DigitalCredentialPaymentMethodData/credentialQuery}}. This data is intended for identity and authorization purposes: identity verification, fraud prevention, and regulatory (KYC) compliance. This specification does not itself make a [=presentation=] adequate for any of these: the assurance a claim carries depends on the issuing authority and assurance level of the underlying [=credential=], and on the merchant's own regulatory obligations, neither of which this [=payment method=] establishes.

Merchants are encouraged to:

  • Use Payment Request-level data for checkout orchestration (tax calculation, shipping, fulfillment).
  • Use [=presentation=] claims for KYC and authorization purposes.
  • Avoid requesting the same data in both places unless there is a specific need for verification of Payment Request-provided data against [=credential=] claims.

If the [=presentation request=] includes address or contact claims, consider whether Payment Request-level collection of the same data is necessary. Duplicate collection creates friction and may confuse users about how their data will be used.

Credential manager requirements

A [=credential manager=] that supports `digital-credential-payment` MUST:

  1. Implement a [=metadata interface=] that:
    • Provides an [=instrument record=] for each available payment [=instrument=], as defined in [[[#metadata-interface-data-model]]].
    • Does not involve Digital Credentials signing.
    • Applies data minimization.
    • Does not leak PII.
  2. Accept signed [=Presentation Requests=] when invoked via the Digital Credentials API and, before producing a [=presentation=], verify:
    • The request's signature (requestor authentication). For OpenID4VP, [[OPENID4VP]] Section 5.9.3 leaves this to the wallet's discretion over the Digital Credentials API; for this [=payment method=] it is required. For "org-iso-mdoc", the request MUST carry reader authentication, and the [=credential manager=] MUST verify it.
    • The origin binding the protocol defines. For signed OpenID4VP requests, this means checking the origin the [=user agent=] conveys against expected_origins ([[OPENID4VP]] Appendix A.2).
    • That the request's amount equals the total the [=user agent=] conveys. For OpenID4VP, that amount is the request's [=payment transaction data=] entry.
    • Other validity constraints (e.g., expiry).
  3. Use only the [=credential=] backing the [=instrument=] the [=user agent=] identifies.
  4. Produce a [=presentation=] that:
    • Satisfies the constraints in the [=presentation request=].
    • Includes a cryptographic holder binding proof for every [=credential=] presented.
    • Is cryptographically bound to that request: to its nonce, to the origin as the protocol requires (for OpenID4VP, an audience of origin: followed by the origin, Appendix A.4), and to its [=payment transaction data=] (see [[[#payment-transaction-data]]]).
  5. Ensure that strong user authentication (e.g., biometrics, PIN) is performed before issuing the [=presentation=]. The [=credential manager=] MAY perform this authentication itself during [=presentation=] creation, or MAY accept an authentication attestation from the [=user agent=] via a platform-defined mechanism when the [=user agent=] has already collected an equivalent authentication for the same transaction (e.g., a biometric prompt at the "Pay" affordance in the payment sheet). When relying on a [=user agent=] attestation, the [=credential manager=] MUST verify that the attestation is bound to the current [=presentation request=] and that the attesting [=user agent=] is one the [=credential manager=] trusts to perform authentication on its behalf; if either property cannot be verified, the [=credential manager=] MUST fall back to performing authentication itself.
  6. Only reveal data in the [=presentation=] that is necessary to satisfy the [=presentation request=] and aligns with credential manager policies and user consent.

Accessibility Considerations

The `digital-credential-payment` [=payment method=] relies on [=user agent=]-controlled payment UI for [=instrument=] selection, price display, and transaction confirmation. [=User agents=] MUST ensure this UI meets accessibility requirements.

Keyboard and input accessibility

  • All interactive elements in the payment sheet — including [=instrument=] selection, the Pay button, and cancellation — MUST be operable via keyboard alone, without requiring a pointing device.
  • [=User agents=] MUST provide visible focus indicators for all interactive elements in the payment UI.
  • [=User agents=] MUST support platform-standard keyboard navigation patterns (e.g., Tab, arrow keys, Enter, Escape) for moving between and activating UI elements.

Screen reader support

  • The payment amount, currency, merchant identity, and selected [=instrument=] MUST be programmatically exposed to assistive technologies.
  • When the payment total changes in response to {{PaymentMethodChangeEvent}} (e.g., a surcharge is applied), [=user agents=] MUST announce the updated total to screen readers using an appropriate mechanism (e.g., ARIA live region or platform accessibility notification).
  • Transitions into the AUTHORIZING and AUTHENTICATING sub-states MUST be announced to assistive technologies via an ARIA live region (or the platform-native equivalent), so that screen-reader users learn the payment is in progress without having to re-traverse the sheet. The progress indicator required by the AUTHORIZING row of the state table MUST itself carry an accessible name.
  • Error messages from {{PaymentAuthorizeEvent/decline()}} or authorization failures MUST be conveyed to assistive technologies, not only displayed visually.
  • [=Instrument=] [=metadata=] displayed in the payment sheet (such as the [=instrument record=]'s display name and network) MUST have accessible names that convey meaningful information to non-visual users.

Focus management

  • When the payment sheet opens ({{PaymentRequest/show()}}), focus MUST move to the payment UI.
  • When the payment sheet closes (resolved or rejected), focus MUST return to the element that triggered the payment flow.
  • During state transitions (e.g., from READY to AUTHORIZING to AUTHENTICATING), focus MUST remain within the payment UI and not be lost.
  • When the merchant rejects the {{Promise}} passed to {{PaymentAuthorizeEvent/respondWith()}} or calls {{PaymentAuthorizeEvent/decline()}}, the resulting transition back to READY MUST restore focus to a stable element within the payment sheet (typically the Pay button) so that keyboard-only users do not lose their place. The same requirement applies to the timeout path: when AUTHORIZING times out, focus MUST be moved to the timeout error message as the sheet returns to READY.
  • [=User agents=] MUST NOT trap focus in the payment UI if the user cancels the transaction.

Authentication accessibility

[=Credential managers=] MUST ensure that user authentication mechanisms (biometrics, PIN entry) are accessible. When biometric authentication is unavailable or fails, [=credential managers=] MUST provide an accessible fallback (e.g., PIN or passcode entry) that is operable via keyboard and compatible with assistive technologies.

Internationalization Considerations

This specification involves user-visible text and currency values that require proper internationalization support.

Display labels and text

  • The display name in an [=instrument record=] SHOULD be localized to the user's preferred language where possible. It is shown only in the payment sheet, never to the merchant.
  • [=User agents=] MUST ensure that the payment UI correctly renders text in all scripts, including bidirectional (BiDi) text for languages written right-to-left.
  • Error messages provided via {{PaymentAuthorizeEvent/decline()}} are merchant-supplied strings. [=User agents=] SHOULD display these messages using the document's language direction and SHOULD render them in a way that handles varying text lengths gracefully.

Metadata value localization

The well-known [=metadata=] values defined in this specification (e.g., {{DigitalCredentialMetadata/network}}, {{DigitalCredentialMetadata/fundingType}}, {{DigitalCredentialMetadata/instrumentType}}) use English-language identifiers as wire values. [=User agents=] MUST translate these identifiers into the user's preferred language when displaying them in the payment UI. The wire values MUST NOT be altered when provided to merchants via {{PaymentMethodChangeEvent}}.

Privacy and Security Considerations

Credential manager invocation and user activation

The Digital Credentials API exposes navigator.credentials.get() as a JS-callable surface that requires transient activation on every call: an attempt to invoke it without an active activation token throws or rejects. That gate exists so that merchant origins cannot trigger a credential manager ceremony without a deliberate user gesture.

This specification's flow already consumes transient activation once: {{PaymentRequest/show()}} is itself gated on and consumes transient activation. By the time the [=user agent=] reaches the AUTHENTICATING sub-state — where the credential manager ceremony actually runs — the page no longer holds a fresh activation token. A literal navigator.credentials.get() call from inside the authorization algorithm would therefore reject with {{"NotAllowedError"}}, which is incompatible with the flow this specification defines.

This specification therefore requires the [=user agent=] to invoke the [=credential manager=] at that point without checking or consuming page activation. The user-intent guarantee that navigator.credentials.get()'s activation gate provides is met at a different layer:

  • The user's "Pay" click in the [=user agent=]-controlled payment sheet is a deliberate activation event sourced from chrome the merchant cannot script. The {{PaymentAuthorizeEvent}} dispatched on that click is the activation moment for the credential manager ceremony.
  • The credential manager ceremony is bound to that click in time: the AUTHORIZING sub-state has a finite, [=user agent=]-enforced timeout (recommended to be at most 30 seconds), after which the sheet returns to READY and a late signed request is ignored. A merchant cannot accumulate signed requests and trigger the credential manager at an arbitrary later moment.
  • The signed request the merchant supplies via {{PaymentAuthorizeEvent/respondWith()}} is bound to the [=instrument=] the user explicitly selected, via the {{DigitalCredentialMethodDetails/instrumentHandle}} mechanism described in this specification.

Re-checking transient activation at that point would therefore be redundant: it would only re-test a property that is already enforced more strongly by the payment sheet's own activation rules.

As written, the Digital Credentials API cannot be invoked this way. Its "prepare credential requests" step, which every credential request reaches (including one made through [[credential-management]]'s request a credential algorithm), rejects with {{"NotAllowedError"}} if the page lacks transient activation, and otherwise consumes it. This specification needs [[digital-credentials]] to define a way to run a credential request after a [=user agent=]-controlled confirmation, without page activation. Until it does, the [=authorize a digital credential payment=] steps cannot complete.

This specification does not change the behaviour of navigator.credentials.get() when it is called directly by a merchant page. Invoking the credential manager without page activation applies only to the [=authorize a digital credential payment=] steps for the "digital-credential-payment" [=payment method=]. Implementations are free to share lower-level credential manager plumbing between the two paths so long as the JS-callable surface continues to enforce its own activation gate.

Process isolation and IPC

This specification deliberately does not specify how the [=user agent=] organises the merchant document, payment-sheet UI, and [=credential manager=] across operating-system processes, nor what IPC mechanisms it uses to move signed [=presentation requests=] and [=presentations=] between them. Both are platform-specific implementation concerns and are out of scope.

What the specification does require is that the trust boundaries described elsewhere in this section hold regardless of the chosen process layout: the merchant document MUST NOT be able to observe the [=metadata interface=] before [=instrument=] selection, the {{DigitalCredentialMethodDetails/instrumentHandle}} MUST NOT be guessable across processes, and the [=user agent=]'s payment sheet MUST remain the sole source of activation for the credential manager ceremony (see [[[#wallet-invocation-and-user-activation]]]). Implementations are free to satisfy these constraints with whatever process and IPC arrangement their platform provides.

Replay attack prevention

Replay protection comes from the presentation protocol, not from this specification. OpenID4VP, for example, requires the merchant to create a fresh, cryptographically random nonce for every request and store it with its session ([[OPENID4VP]] Section 5.2), and requires the [=credential manager=] to bind the [=presentation=] to that nonce and to its audience (Section 14.1; over the Digital Credentials API the audience is the origin, Appendix A.4). The merchant's server checks both before accepting the [=presentation=].

Every authorization attempt obtains a fresh signed request, including a retry after a decline, a timeout, or a [=credential manager=] failure, so each attempt carries a fresh nonce. A merchant that pre-signs requests (see [[[#optimistic-signing]]]) discards a pre-signed request once it has been used. Because the request also carries [=payment transaction data=] that the [=credential manager=] binds into the [=presentation=], a captured [=presentation=] cannot be reused to authorize a different amount.

Request tampering

The signed [=Presentation Request=] protects against request tampering by malicious intermediaries through layered checks at the [=user agent=], the [=credential manager=], and within the credential format itself.

  • [=User agents=] MUST [=validate the signed request=]: the amount in its [=payment transaction data=] must equal the current payment total surfaced in {{PaymentAuthorizeEvent/total}}, and its dcql_query must equal the merchant's {{DigitalCredentialPaymentMethodData/credentialQuery}}. A mismatch MUST fail the request with a {{"SecurityError"}}.
  • [=User agents=] MUST verify that the {{PaymentAuthorizeRespondOptions/instrumentHandle}} passed to {{PaymentAuthorizeEvent/respondWith()}} matches the token most recently issued for the current {{PaymentRequest}} (see [[[#credential-substitution-attacks]]]); a mismatch MUST fail the request with a {{"SecurityError"}}.
  • [=Credential managers=] MUST verify the cryptographic signature on the [=Presentation Request=] before constructing a [=presentation=]. The signature MUST cover the request's critical fields, at a minimum the transaction amount, [=credential=] constraints, and nonce.
  • [=Credential managers=] MUST verify the request's origin binding as the protocol defines (for signed OpenID4VP requests, expected_origins) before producing a [=presentation=] (see [[[#merchant-identity-binding]]]).

The [=user agent=] reads only the [=payment transaction data=] and dcql_query of the signed request; see [[[#signed-request-validation]]]. The [=credential manager=] ceremony remains the authoritative consent surface for the claims that are released.

Credential substitution attacks

An attacker might attempt to substitute a different [=credential=] during the Digital Credentials API flow than the one displayed to the user during checkout.

This specification provides two complementary layers of protection against credential substitution:

Selection binding via instrumentHandle

The {{DigitalCredentialMethodDetails/instrumentHandle}} token provides a [=user agent=]-verified binding between the [=instrument=] selection and the merchant's authorization:

  • The [=user agent=] generates an ephemeral, opaque {{DigitalCredentialMethodDetails/instrumentHandle}} each time the user selects an [=instrument=], and provides it to the merchant via the {{PaymentMethodChangeEvent}}.
  • The merchant passes this {{DigitalCredentialMethodDetails/instrumentHandle}} as |options|.{{PaymentAuthorizeRespondOptions/instrumentHandle}} on the second argument to {{PaymentAuthorizeEvent/respondWith()}}. The {{DigitalCredentialMethodDetails/instrumentHandle}} is not a member of the signed [=presentation request=] itself.
  • The [=user agent=] MUST validate that |options|.{{PaymentAuthorizeRespondOptions/instrumentHandle}} matches the token associated with the currently selected [=instrument=] before routing the request to the [=credential manager=]. The check happens as soon as dispatch of the {{PaymentAuthorizeEvent}} completes; a mismatch MUST fail the request with a {{"SecurityError"}}.

This ensures that the merchant's authorization — including any pricing adjustments based on [=instrument=] [=metadata=] — is bound to the specific [=instrument=] the user selected. The binding is enforced by the [=user agent=], which compares |options|.{{PaymentAuthorizeRespondOptions/instrumentHandle}} against its internally stored token before invoking the Digital Credentials API.

The {{DigitalCredentialMethodDetails/instrumentHandle}} is not a defence against a compromised merchant page: scripts running at the merchant origin can read the handle from the {{PaymentMethodChangeEvent}} and pass it to {{PaymentAuthorizeEvent/respondWith()}}. What it prevents is the merchant authorizing a stale selection, such as a request priced for an [=instrument=] the user has since replaced. The browser-to-credential-manager binding (described below) provides a defense-in-depth layer that operates independently of merchant cooperation.

Browser-to-credential-manager binding

The internal [=instrument=]-to-[=credential=] binding is enforced by the [=user agent=] and [=credential manager=]:

  • [=User agents=] MUST enforce binding between the [=instrument=] selected in the Payment Request UI and the [=credential=] used in the Digital Credentials API invocation.
  • The internal [=instrument=] identifier passed to the Digital Credentials API MUST be opaque to the merchant to prevent merchant-initiated substitution attacks.
  • [=Credential managers=] MUST only use the [=credential=] corresponding to the provided [=instrument=] hint.

The [=credential manager=] is responsible for ensuring correct [=credential=]-to-[=instrument=] mapping. The [=user agent=] provides an opaque, credential-manager-scoped handle identifying the selected [=instrument=], and the [=credential manager=] MUST resolve this handle to the correct [=credential=] internally.

Merchant identity binding

A [=presentation=] must be usable only by the origin that requested it. Rather than defining a check of its own, this specification relies on the binding that the Digital Credentials API and the presentation protocol already provide:

  • The [=user agent=] conveys the requesting origin to the [=credential manager=] alongside the request, as the Digital Credentials API does for any credential request.
  • For signed OpenID4VP requests, the [=credential manager=] MUST compare that origin with the request's expected_origins and refuse the request if it is not listed ([[OPENID4VP]] Appendix A.2).
  • The [=credential manager=] binds the [=presentation=] to the origin. For OpenID4VP, the audience is origin: followed by the origin, even for signed requests (Appendix A.4), and for mso_mdoc credentials the origin is part of the session transcript (Appendix B.2.6.2). For "org-iso-mdoc", the binding is as ISO/IEC 18013-7 defines. The merchant's server verifies this binding.

The [=user agent=] does not interpret the request's client_id. OpenID4VP Client Identifiers carry prefixes (e.g., x509_san_dns:, decentralized_identifier:) whose verification belongs to the [=credential manager=]'s trust framework.

Together, these prevent a malicious page at attacker.example from replaying a request signed by victim.example: the signed request lists only victim.example's origins in expected_origins, and any [=presentation=] produced is bound to the origin that actually made the request. In a cross-origin iframe, the requesting origin is the iframe's (for example, a payment service provider's), so that is the origin that must appear in expected_origins.

Defence against merchant-origin XSS

A cross-site scripting (XSS) compromise of the merchant origin can intercept the {{PaymentAuthorizeEvent}}, read the {{DigitalCredentialMethodDetails/instrumentHandle}} from page state, and call {{PaymentAuthorizeEvent/respondWith()}} with a request of its choosing. Origin binding does not help: the attacker's script runs at the merchant's own origin, so any [=presentation=] it obtains is bound to the right origin. The defences are:

  • Signed requests. This specification requires the final request to be signed (see [[[#supported-presentation-protocols]]]), and the [=credential manager=] MUST verify the signature. The attacker cannot produce the merchant's signature, so it cannot substitute its own response-encryption key (which would let it decrypt the [=presentation=]) or its own transaction data. Replaying one of the merchant's genuinely signed requests gains nothing: the [=presentation=] is encrypted to the merchant's key, and the merchant's server accepts each nonce only once.
  • The [=user agent=] constrains the Digital Credentials API invocation to the [=credential=] backing the [=instrument=] the user selected, so an XSS attacker cannot cause a different [=instrument=] to be used. The {{DigitalCredentialMethodDetails/instrumentHandle}} adds nothing here, since the attacker can read it from page state.

These defences are partial. An XSS attacker can still do anything the merchant page can, such as changing the total through {{PaymentRequestUpdateEvent/updateWith()}} (which the user sees in the payment sheet) or reading whatever the merchant's server returns to the page. Merchants are strongly encouraged to deploy Content Security Policy [[CSP3]] and Subresource Integrity [[SRI]], and to sign requests on their server, never in the page.

Man-in-the-middle protection

This specification relies on transport-layer security to protect against network-level attackers.

  • {{PaymentRequest}} and {{PaymentAuthorizeEvent}} are only exposed in secure contexts, so the merchant page is served over HTTPS. Merchants should likewise use HTTPS for their signing endpoint.
  • The Digital Credentials API invocation MUST NOT transmit the [=Presentation Request=] or [=presentation=] over unencrypted channels.
  • [=Credential managers=] MUST verify the request's origin binding as described in [[[#merchant-identity-binding]]].

Cross-origin and permissions policy

The `digital-credential-payment` [=payment method=] involves two capability-gated APIs: the Payment Request API and the Digital Credentials API. [=User agents=] MUST enforce permissions policy for both when this [=payment method=] is used in cross-origin contexts.

  • The "payment" permissions policy [[payment-request]] MUST be enabled for the context in which the {{PaymentRequest}} is constructed. In cross-origin <iframe> elements, the allow="payment" attribute MUST be present.
  • The "digital-credentials-get" permissions policy [[DIGITAL-CREDENTIALS]] MUST be enabled for the Digital Credentials API invocation. In cross-origin <iframe> elements, the allow="digital-credentials-get" attribute MUST be present.
  • When the `digital-credential-payment` [=payment method=] is used from a cross-origin <iframe>, both permissions policies MUST be enabled. The <iframe> element MUST include allow="payment; digital-credentials-get".

If either permission is not granted, the [=user agent=] MUST NOT route the signed request to the [=credential manager=] and MUST reject the {{PaymentRequest/show()}} {{Promise}} with a {{"SecurityError"}} {{DOMException}}.

Merchants embedding payment flows in cross-origin iframes must ensure both permissions are explicitly delegated. A common deployment pattern is a payment service provider (PSP) iframe; the embedding page must grant both payment and digital-credentials-get permissions to the PSP origin.

Phishing and UI spoofing

  • [=User agents=] MUST present payment UI using trusted, browser-controlled surfaces that cannot be spoofed by web content.
  • The payment amount, merchant identity, and selected [=instrument=] MUST be clearly displayed in trusted UI.
  • [=User agents=] SHOULD provide visual indicators to distinguish authentic payment UI from web-rendered imitations.
  • Strong user authentication (biometrics, PIN) MUST occur in a trusted, non-web-content surface — either [=credential manager=]-controlled UI or [=user agent=]-controlled payment-sheet UI — and MUST NOT be solicited or rendered by the merchant page.

Fingerprinting risks

The [=metadata interface=], if not carefully constrained, could enable merchant fingerprinting through [=credential=] enumeration.

  • The [=metadata interface=] MUST only expose coarse-grained information (network, brand, funding type) that has high entropy overlap across users.
  • [=User agents=] SHOULD limit the granularity of [=metadata=] to prevent unique identification based on [=credential=] portfolio.
  • [=User agents=] MAY require user gesture or consent before exposing any [=metadata=] to merchants.
  • The number and types of available [=credentials=] MUST NOT be exposed to merchants.
  • High-cardinality fields SHOULD be bucketed into common categories to reduce fingerprinting entropy.
  • [=Credential manager=]-specific identifiers MUST NOT be exposed to merchants.

instrumentHandle privacy properties

The {{DigitalCredentialMethodDetails/instrumentHandle}} token is designed to avoid introducing new tracking vectors while providing the necessary binding between [=instrument=] selection and the signed [=Presentation Request=]:

  • The token MUST be ephemeral — a new value is generated each time the user selects an [=instrument=], with no persistence across sessions or page loads.
  • The token MUST be opaque — it MUST NOT encode any information about the [=instrument=], [=credential=], [=credential manager=], or user.
  • The token MUST NOT be correlatable across origins, sessions, or transactions. Two different selections of the same [=instrument=] MUST produce different tokens.
  • The token MUST be a version 4 UUID [[RFC9562]].
  • The token MUST NOT be reused or recycled from previous transactions.

Because the {{DigitalCredentialMethodDetails/instrumentHandle}} is freshly generated on each selection, carries no information about the underlying [=instrument=], and cannot be correlated across sessions, it does not increase the fingerprinting surface of the API beyond what the existing [=metadata=] already provides.

Correlation attacks

Merchants might attempt to correlate users across sessions or across merchant sites using [=credential=] [=metadata=] or [=presentation=] contents.

  • [=presentations=] MUST NOT include persistent identifiers unless explicitly required by the [=credential=] type and disclosed to the user.
  • Different presentations for the same [=credential=] MUST NOT be linkable across origins unless explicitly required by the [=credential=] scheme and disclosed to the user.
  • The [=user agent=] can see the claims the merchant's {{DigitalCredentialPaymentMethodData/credentialQuery}} asks for, but cannot judge whether they exceed what the payment requires; minimising the claim set therefore rests on the [=credential manager=] disclosing the request during its ceremony and on selective disclosure. A [=user agent=] SHOULD warn the user when {{DigitalCredentialPaymentMethodData/credentialQuery}} asks for claims beyond what is necessary for payment.
  • [=Credential managers=] SHOULD support selective disclosure where the [=credential=] format permits.
  • [=Credential managers=] SHOULD use per-origin pseudonymous identifiers when supported by the [=credential=] format.

Data minimization

  • [=Credential managers=] MUST only include claims explicitly requested in the [=Presentation Request=] and necessary for the transaction.
  • The [=Presentation Request=] format SHOULD support requesting specific claims rather than entire [=credentials=].
  • [=User agents=] SHOULD display to users exactly which claims will be shared before [=presentation=] creation.
  • [=Credential manager=] implementations SHOULD prefer [=credential=] formats that support selective disclosure (e.g., SD-JWT, BBS+ signatures).

User consent

  • [=User agents=] MUST display clear information about the merchant identity, transaction amount, and requested claims before [=presentation=] creation.
  • [=User agents=] MUST require explicit user confirmation of the transaction through a trusted UI control.
  • Consent for [=metadata=] sharing (during price negotiation) and [=presentation=] creation (at final confirmation) MAY be separate consent flows.
  • [=User agents=] SHOULD provide a mechanism for users to review and modify which optional claims are included before presentation.

Open issues

The following issues remain open for discussion:

Well-known payment credential types
{{DigitalCredentialPaymentMethodData/credentialQuery}} identifies [=credentials=] by format-specific type identifiers (SD-JWT VC vct values, mdoc doctypes, W3C VC types). Merchants and issuers would benefit from well-known identifiers for payment credentials. Defining them is outside this specification's scope, but the working group should coordinate with the ecosystems that define them.
Metadata interface interoperability

The data the [=metadata interface=] carries is defined in [[[#metadata-interface-data-model]]], but its transport is intentionally platform-specific (see [[[#design-assumptions]]]). Three resulting interoperability risks are acknowledged:

  • Two conforming [=user agents=] running on the same platform may surface different [=instrument=] sets for the same user, with no spec-defined recourse.
  • The Digital Credentials API routes requests to [=credential managers=] registered with the platform, including third-party ones, and does not currently define web-based [=credential managers=]. If it comes to support them, the [=metadata interface=] would need a corresponding transport.
  • The synchronization window is unspecified, so "out of date" has no portable definition.

The working group should pursue a companion specification defining (a) a common transport and discovery mechanism for [=instrument records=] that any [=credential manager=] can implement, independent of platform, and (b) a freshness contract with portable bounds. The [=metadata interface=] could also require user consent or a user gesture before exposing [=instrument=] [=metadata=] to merchants; that decision belongs to the same companion work.

Metadata value-set registry

§[[[#entropy-constraints]]] requires {{DigitalCredentialMetadata}} values for network and instrumentType to be drawn from a finite, [=user agent=]-controlled set, but does not enumerate the values. This defers agreement on the full set of payment networks and instrument types, at the cost of an interoperability gap: two conforming [=user agents=] can surface different identifier strings for the same underlying property (e.g., "americanexpress" vs. "amex").

The working group should establish a registry — IANA-style or W3C-tracked, modeled on the Payment Method Identifiers registry pattern — that defines:

  • The initial value set for each field (network, instrumentType) and any future additions.
  • An extension policy gated on a privacy review against the entropy and fingerprinting constraints in §[[[#entropy-constraints]]], on the same basis as new {{DigitalCredentialMetadata}} keys.
  • A canonical wire form for each value (case, character set, length bound).

Once such a registry exists, this specification will be reframed to require values be drawn from it, replacing the current [=user agent=]-controlled-set rule.

Generic authorize-window hook
The {{PaymentRequest/onpaymentauthorize}} attribute and the {{PaymentAuthorizeEvent}} are method-private to `digital-credential-payment`, and the [=authorize a digital credential payment=] steps assume a pre-acceptance point that [[payment-request]] does not define (see [[[#authorizing-a-payment]]]). The working group should coordinate with the Web Payments WG on whether [[payment-request]] should expose a generic authorize-window hook reusable by other payment methods. If such a hook is defined, this specification will reframe its use of partial interface PaymentRequest against the new hook.
Activation-gate bypass formalisation
§[[[#wallet-invocation-and-user-activation]]] requires the [=user agent=] to invoke the [=credential manager=] without page transient activation, which the Digital Credentials API's "prepare credential requests" step does not currently allow. The working group should file a coordination issue against [[digital-credentials]] proposing a hook for credential requests made after a [=user agent=]-controlled confirmation, and reframe this specification against it once it lands.
User-agent authentication attestation

The [[[#wallet-requirements]]] section permits a [=credential manager=] to accept an authentication attestation from the [=user agent=] in lieu of performing its own biometric/PIN ceremony, when the [=user agent=] has already collected an equivalent authentication for the same transaction.

However, [[DIGITAL-CREDENTIALS]] does not currently define a mechanism for a [=user agent=] to convey such an attestation to a [=credential manager=], or for a [=credential manager=] to verify that the attestation is bound to the current [=presentation request=] and comes from a [=user agent=] it trusts. Until it does, there is no interoperable way for a [=credential manager=] to rely on authentication performed by the [=user agent=].

PaymentMethodChangeEvent.methodDetails compatibility
{{DigitalCredentialMethodDetails}} is delivered to the merchant via {{PaymentMethodChangeEvent/methodDetails}}, which [[payment-request]] currently types as object?. The Web Payments WG should confirm that a typed dictionary subtype delivered through this slot is in scope, or if a parent-spec clarification is required.
Authorization Latency
The {{PaymentAuthorizeEvent}} introduces a network round-trip at the moment of user confirmation. Implementations should optimize this path.
Multiple Credentials
This proposal assumes a single [=instrument=] per payment. Future work may extend this method to support composite presentations.

This specification defines conformance criteria for two classes of products:

Conforming user agent
A [=user agent=] that implements the `digital-credential-payment` [=payment method=] as defined in this specification.
Conforming credential manager
A [=credential manager=] that implements the [=metadata interface=] and [=credential=] presentation requirements as defined in this specification.

A conforming [=user agent=] MUST:

  • Implement the processing model defined in this specification.
  • Fire {{PaymentMethodChangeEvent}} events only after user interaction.
  • Fire {{PaymentAuthorizeEvent}} events before Digital Credentials API invocation.
  • Validate the merchant's signed request per [[[#signed-request-validation]]].
  • Convey the requesting origin and the payment total to the [=credential manager=] alongside the request.
  • Enforce anti-enumeration requirements.
  • Enforce [=credential=] substitution protections via opaque handles.
  • Generate a cryptographically random {{DigitalCredentialMethodDetails/instrumentHandle}} on each [=instrument=] selection, provide it to the merchant via {{PaymentMethodChangeEvent}}, and validate the value passed to {{PaymentAuthorizeEvent/respondWith()}} against the current selection before routing the request to the [=credential manager=].

A conforming [=credential manager=] MUST meet the requirements specified in the [[[#wallet-requirements]]] and [[[#payment-transaction-data]]] sections, and any other requirements this specification places on [=credential managers=].

Guidance addressed to merchants (for example, on signing endpoints, nonces, and Content Security Policy) is informative: merchants are not a conformance class of this specification.

[=User agents=] MAY implement algorithms given in this specification in any way desired, so long as the end result is indistinguishable from the result that would be obtained by the specification's algorithms.
